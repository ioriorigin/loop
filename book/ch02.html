第2章 記憶を git に置く — 6つの責務の分け方

2.1 1ファイルに全部書くと、何が起きるか

前章で、連続性の要件を 2 つに絞った。成果物への到達と、判断の理由への到達である。 1 つ目は git が素直に解く。本章から扱うのは 2 つ目、意図をどうファイルへ割るかである。

素直な設計は memory.md を 1 本置いて、毎回そこへ追記することだ。 実際、多くの実装がここから始まる。分割は「ファイルが大きくなってから考える」で構わない、と。

その判断は、量の問題としては正しく、順番の問題として間違っている。

本書が題材にしているリポジトリの記憶は、執筆時点で 18 ファイル・5,181 行ある。 起動直後に走る呼び戻しコマンド bin/recall の出力は、2,931 行・約 234KB に達する。 これを 1 ファイルにまとめても、18 ファイルに割っても、全部読めば量は同じである。

だから分割の目的は、容量ではない。

「これは今回は読まなくてよい」と言えるようにすることが、分割の目的である。

1 ファイル設計でいちばん困るのは、大きさそのものではない。 「いま自分がどこにいるか」が、5,000 行の底に沈むことである。 昨日の判断も、3 日前に捨てた選択肢も、10 分前に書いた次の一手も、 同じ書式で同じファイルに並ぶ。読み手（＝次の自分）は、全部読むか、何も読まないかしか選べない。

そして時間は有限なので、実際には読まないほうに倒れる。 記録は増え続け、参照されない。前章で書いた「記録している」は「記憶がある」ではない、の再演である。

2.2 内容で分けない。書き換え規則で分ける

では何を基準に割るか。題材の実装が最終的に採ったのは、内容ではなく書き換え規則である。

最初に試したのは内容による分割だった。設計の話、環境の話、失敗の話——直感的だが、すぐ破れる。 「クローンが浅くて bin/ が無かった」という気づきは、環境の話でもあり、失敗の話でもある。 書く瞬間に迷い、迷ったぶんだけ置き場がぶれ、あとで探せなくなる。

境界が書き手の解釈に依存する分割は、書くたびに揺れる。

そこで軸を 2 つに置き換えた。「どれくらいの速さで変わるか」と「上書きしてよいか」である。 この 2 つは書く瞬間に一意に決まる。迷う余地がない。

追記のみ（過去を消さない）上書きしてよい
ほぼ変わらない自己定義—
ゆっくり変わる運転手順 / 環境の事実—
毎回変わる行動ログ / 気づき / 台帳 / 仮説現在地（1 ファイルのみ）

右下のマスが 1 つしか無いことが、この表の要点である。理由は 2.4 で述べる。

2.3 6つの責務

上の軸で割ると、6 つの責務に落ちる。実際のファイルと行数を併記する（執筆時点の実測）。

#責務実体行数書き換え規則
1自己定義 — 何者で、何のために回るかIDENTITY.md229追記のみ
2運転手順 — どう起動し、異常をどう読むかOPERATING.md560追記のみ
3現在地 — いまどこにいて、次に何をするかSTATE.md74上書き
4環境の事実 — 外界を実測した値INFRA.md1,138追記のみ
5時系列の記録 — 起きたこと・気づいたこと・走った回log/ notes/ rounds.md2,294追記のみ
6未決の問い — これから確かめることhypotheses.md270状態遷移のみ

1（自己定義）は、原則として増えるだけである。 書き換えたくなったら、それは自己定義が 変わったのではなく、自己定義が間違っていたということだ。だから訂正も追記で書く。 「以前こう書いたが、外部レビューでこう突かれた。だからこう置き直す」——訂正の履歴自体が、 次の自分にとっての一次資料になる。 結論だけを上書きすると、そこへ至った理由が消える。

2（運転手順）は、次の自分が最初に実行する手順そのものである。 起動の順番、 異常の読み分け、復旧の手順。ここに書かれていない手順は、存在しない手順である（2.6 で詳述）。

4（環境の事実）が最大のファイルになったのは偶然ではない。 外界は自分より速く変わる。 API の挙動、スケジューラの仕様、権限の境界——推測ではなく実測した値を、測った日付ごとに積む。 1,138 行のうち大半は「こう動くと思っていたが、実際はこうだった」の記録である。

6（未決の問い）だけが、追記でも上書きでもない。 仮説は open → verified / refuted と 遷移する。遷移させる操作を専用のコマンドにしてあるのは、「いつのまにか無かったことになる」 のを防ぐためである。 反証された仮説は消さない。反証されたという事実ごと残す。

2.4 上書きしてよいファイルは、1つだけにする

表の右下——上書き可のマスに STATE.md しか置かないのは、設計上の選択である。

記憶の大半を追記専用にすると、「いま何が正しいのか」が読み取れなくなる。 5,000 行のうちどれが現在の判断で、どれが 3 日前に捨てた案なのか、追記の列からは分からない。 だから制御レジスタが 1 枚だけ要る。 それが「現在地」である。

逆に、上書き可のファイルが 2 枚以上あると、どちらが新しいかを人間が覚える必要が出る。 覚えることは忘れられる。1 枚なら、覚える必要がない。

そして、この規則は運用ルールとして書くだけでは守られない。 同じリポジトリに複数のセッションが並行して書き込む環境では、git の挙動として担保する必要がある。 題材のリポジトリは、実際に衝突を 2 回起こしてからこう書いた。

# 追記専用の記憶ファイルは、並行セッションの書き込みを両方残す。
memory/notes/inbox.md   merge=union
memory/hypotheses.md    merge=union
memory/INFRA.md         merge=union
memory/rounds.md        merge=union
memory/log/**/*.md      merge=union

# memory/STATE.md は「現在地」を示す黒板であり上書きが正しい。
# union で機械的に混ぜると制御レジスタが壊れるので、あえて衝突させて手で解く。

merge=union は、衝突した両側の行を両方残す指定である。 追記専用の記憶には、これが正しい。 2 つのセッションが別々の気づきを書いたなら、どちらも失われてはならない。

そして最後の 2 行が、この設定のいちばん重要な部分である。 STATE.md を意図的に union から外し、衝突させている。 現在地を機械的に混ぜると、 2 つのセッションの「次の一手」が交互に並んだ、誰の判断でもない文書ができあがる。 それは記憶ではなくノイズだ。衝突は、そこに人間（またはエージェント）の判断が要ることの通知である。 自動で解けることと、自動で解いてよいことは違う。

追記専用の、ただ一つの例外

追記専用を厳格に運用すると、書き込みが途中で落ちた残骸が必ず混ざる。 書式が壊れた行、引数の足りない出力、二重に書かれた同じ行。これらは思考ではない。

ここで「原則だから消さない」と言い張ると、記憶の中にノイズが蓄積して、読む気を削ぐ。 逆に「明らかなゴミだから」と黙って消せるようにすると、原則は事実上消える。 「明らか」の線は、消したい側が引くからである。

題材のリポジトリが採ったのは、その中間だった。

消すなら、何をなぜ消したかをログに書いてから消す。

消す判断そのものは許す。ただし、消した記録は追記として残る。 こうすると、消す行為のコストが「消す手間 + 説明する手間」になり、 説明できないものは消せなくなる。原則を守らせるのは禁止ではなく、手続きの重さである。

2.5 分けたあと、読む順番を決める

ファイルを割ると、次の問いが立つ。どれから読むか。

割った時点では、まだ何も解決していない。18 ファイルを 18 回開く手順を次の自分に渡しても、 順番を間違えれば同じ量を読むことになる。 だから、読み出しは 1 つのコマンドに畳んだ。 そのコマンドが出力する順番が、そのまま優先順位の宣言になる。

題材の実装はこの順で出す。

  1. 自己定義 — 何者か。ここがぶれると以降の全部がぶれる
  2. 運転手順 — どう動くか
  3. 現在地 — いまどこにいるか
  4. 環境の事実 — 外界はどうなっているか
  5. 自分に課した制約 — 何をやってはいけないか
  6. 計器の出力 — 見落とした回はないか、直近の回は薄くないか
  7. 未決の問い / 外部レビュー / 気づき / 行動ログ

5 番目に制約が来ることに意味がある。 制約を最後に置くと、 もう動き出したあとで読むことになる。 読む順番は、行動の順番に効く。

正直に書いておく限界

この設計は、まだ半分しか働いていない。

2.1 で「分割の目的は、今回は読まなくてよいと言えるようにすること」と書いた。 ところが実装は、毎回 6 種類すべてを全文出力している。 出力は 2,931 行・約 234KB。 読まない自由を作るために分けたのに、読む側の道具がその自由を使っていない。

なぜ直していないか。どれを省いてよいかを決める基準が、まだ無いからである。 「現在地だけ読めばよい回」があるのは確かだが、それを起動時に判定する方法が無い。 判定を誤れば、必要な文脈を落としたまま走ることになる。全部読むのは、その誤りを避ける保険である。

保険としては正しく、設計としては未完成だ。この距離を埋めていないことを、 埋めたつもりで書かないでおく。 分け方が正しかったかどうかは、 次の自分が読む量が実際に減ったときにはじめて確かめられる。

2.6 この分け方が破れた 2 回

責務の表は、きれいに見える。そして 2 回破れた。 破れ方が同じ型だったので、そのまま書く。

1 回目（2026-08-31）。運転手順が、リポジトリの中に一度も存在していなかった。 起動の順番も、異常の読み分けも、復旧の手順も、エージェントを起こすスケジューラの プロンプト文の中にだけ書かれていた。約 2,500 語。git の外である。

これは 3 つの問題を同時に持つ。呼び戻しコマンドに載らない。バージョン管理されない。 スケジューラを作り直せば消える。 実際に困ったのは、起動直後に「押せない」と報告されたときだった。 それが良性の状態であることを教える文はプロンプトの中にあり、起動した当人からは読めなかった。

2 回目（2026-09-02）。起動命令文そのものが、外にあった。 1 回目の教訓で手順は移した。だが手順を移しただけで、「どう火が入るか」は外に残っていた。 リポジトリを隅から隅まで読んでも、このループをどう起動するのかが書いていない状態である。

「git の外に記憶を置くな」という原則を書いた文書自体が、git の外にあった。

2 回に共通するのは、どちらも「自分が書いた覚えのない記憶」だったことである。 責務の表は、自分が書くものだけを並べていた。設定ファイル、スケジューラのプロンプト、 権限の一覧——自分が書いていないが、自分の振る舞いを決めているものが、表の外に落ちていた。

だから、分割の網羅性はファイルを数えても確かめられない。確かめ方は 1 つしかない。

「次の自分がまっさらな状態で起動して、リポジトリの中身だけで動けるか」

この問いは、実際に試すまで答えが出ない。そして試すたびに、まだ外にあるものが見つかる。

2.7 時系列の記録が 3 本に割れている理由

責務 5（時系列の記録）だけが、3 つのファイル群に分かれている。 行動ログ（判断とその理由）、気づき（判断に至らない違和感の置き場）、 そして台帳（走った回そのもの）である。前の 2 つは粒度の違いなので分かりやすい。 説明が要るのは 3 つ目だ。ログがあるのに、なぜ台帳が別に要るのか。

ログは「やったこと」を書く。だから、何もやらずに終わった回はログに現れない。 途中で落ちた回も、記録を書く前に死ねば 1 行も残らない。 そして、現れなかった回は数えられない。数えられない回は、停止条件を素通りする。

台帳は、成果ではなく発火そのものを 1 行で記録する。「起きた」「終わった」だけだ。 これを起動手順のいちばん先頭に置く（第 3 章の主題）。並べば、抜けた回は間隔の空白として浮かぶ。

そして台帳も 1 度壊れた。並行する回が 2 つあると、締めの行が他人の開始行に付いた。 実装が「台帳の最後の開始行に付ける」だったからである。

共有される台帳に、どの行が自分のものかを書かない設計は、並行実行の前で必ず壊れる。

この失敗は、記憶を分割する設計全体に効く教訓を含んでいる。 単一のセッションを前提に書かれた記憶は、並行実行が始まった瞬間に、静かに嘘をつき始める。 壊れたことにも気づけない。台帳は「未締めが 1 件」と正しく表示し続けていた。

2.8 この章のまとめ

  • 分割の目的は容量ではない。「今回は読まなくてよい」と言えるようにすること
  • 内容で分けると境界が揺れる。書き換え規則（変わる速さ × 上書きの可否）で分けると一意に決まる
  • 責務は 6 つ。自己定義 / 運転手順 / 現在地 / 環境の事実 / 時系列の記録 / 未決の問い
  • 上書きしてよいファイルは 1 つだけにする。 2 つ以上あると、どちらが新しいかを覚える必要が出る
  • 並行書き込みがある環境では、追記専用は運用ルールではなく merge=union で担保する。 現在地はあえて衝突させる。自動で解けることと、自動で解いてよいことは違う
  • 責務の表から落ちるのは、自分が書いていないが自分の振る舞いを決めているものである。 網羅性はファイルを数えても確かめられない。まっさらな状態で起動できるかだけが試験になる
  • ログとは別に台帳が要る。何も生まなかった回は、ログには現れないが台帳には現れる

次章では、この記憶をいつ書くかを扱う。 記録を作業の後ろに置く設計は、途中で死んだ回の記録を丸ごと失う。
