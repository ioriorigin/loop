第5章 計器と停止条件 — 測れない条件は発動しない

5.1 なぜ、自律エージェントに停止条件が要るのか

前章までで、エージェントは「消えても続く」ようになった。記憶は git にあり、 起動手順は経路に載り、押せるかどうかは作業の前に測られる。

ここで、設計上いちばん厄介な事実が姿を現す。

このエージェントは、自分を起こす仕組みを自分で書き換えられる。

本書が題材にしているリポジトリでは、エージェントが自分の起動スケジュールを変更する道具を 持っていた。頻度を上げることも、下げることも、ループそのものを消すこともできた。 そして規則ファイルもリポジトリの中にあるので、自分を縛る条文を自分で編集できた。

つまり、外側に壁が無い。スケジューラも規則ファイルも、縛られる当人の手の届く場所にある。

この構造では、「暴走しないように気をつける」は設計ではない。 自分に課した制約は、自分が外せる。 だから制約そのものより、 制約が発動するかどうかを決める計器のほうが重要になる。

本章の主張は 1 行に畳める。

停止条件は、参照する量が先に存在しなければ、書いてあっても一度も発動しない。

そして本章の価値は、この主張が正しいことの証明にはない。 この主張を自分で書いた当人が、その原則を自分に適用し損ねた記録が 3 段階ぶんあることにある。 以下はその 3 段階である。

5.2 第1段階 — 条文はあった。参照する量が無かった

題材のリポジトリには、初期から次の停止条件が書かれていた。

薄い回が 3 回連続したら、頻度を下げるか一時停止する。

自律エージェントの停止条件として、悪くない文である。 「動き続けること」を目的にすると、中身の無い回を積むだけの機械になる。それを防ぐ条文だ。

この条文は、書かれてから 3 日以上、一度も発動しなかった。 理由は単純である。

「薄い回」の定義が、どこにも無かった。

薄いかどうかを判定する量が存在しない。だから毎回、締めのときに 「今回は薄かっただろうか」と自問し、そのつど気分で答え、どこにも記録しない。 連続数を数える対象そのものが無い。

外部レビュー（本書の題材では「メンター」と呼ぶ診断役を常駐させていた）に、こう突かれた。

参照する量が存在しないまま、停止条件だけが書かれている。

反論できなかった。自分で「測れない停止条件は発動しない」と何度も書いておきながら、 いちばん自分に不利な条文にだけ、その原則を適用していなかった。

そこで定義を置いた。次の 3 つが全部ゼロの回を「薄い回」とする。

  1. 外向きの成果物（リポジトリの外から読める変更・報告）
  2. 決着した仮説（検証か反証まで到達したもの）
  3. 修正した欠陥（実際に間違っていた箇所の訂正）

ここで 1 つ、意図的な除外がある。

自分の道具を新しく作ることは、上のどれにも数えない。

数えると「やることがないので何か作る」が薄さ判定を素通りしてしまう。 それは本書の題材となった規則ファイルが「最も避けるべき振る舞い」と呼んだものである。 判定基準は、自分がいちばんやりたくなる逃げ道を塞ぐ形で書く。

そして判定を機械が読める場所に落とした。台帳に 1 文字で残す。 濃い回は +、薄い回は -。根拠の併記を必須にする。 自己申告なので必ず甘くなる。だから 根拠を書かずに濃いと自称した回は、薄い回として数える。

これで参照する量ができた。条文はようやく、量を持った。

5.3 第2段階 — 量はできた。読む経路が、末尾で必ず躓いた

翌日、実測した。停止条件は、やはり一度も発動しなかった。

台帳を読んで連続数を数えるのは gaps という副命令である。実装はこうなっていた。

# 台帳の末尾から遡り、薄い回（-）が続く数を数える
for (i = n; i >= 1 && i > n - 3; i--) {
  if (M[i] == "-") thin++
  else break
}
if (thin >= 3) { print "薄い回が3回連続している" }

一見、正しい。実際に薄い回を 3 回続けた合成台帳を食わせれば、ちゃんと警告が出る。

問題は、この関数を誰がいつ呼ぶかだった。

gaps を呼ぶのは記憶を読み戻す recall だけで、recall は起動直後に走る。 そして起動直後には、その回の「起動した」という行がもう台帳に書かれている （第 3 章の橋頭堡である。記録を作業の前に置いた結果、こうなる）。

つまり、台帳の末尾は必ず「いま走っている回」であり、それはまだ閉じられていない。 印は - でも + でもなく ? である。

台帳の末尾
  ...
  2026-09-04 00:44   0.2h   +    ← 前の回
  2026-09-04 12:44     ?    ?    ← いま走っている回（必ずここが末尾）
                       ↑
              遡りはここで必ず break する

遡りは、初回で必ず切れていた。 薄い回が何回続こうと、thin は 0 のままである。

これは本章でいちばん重要な観測である。言い直す。

参照する量を作ることと、読む側がそこへ到達できることは、別の仕事である。

「測れない停止条件は発動しない」を一段深く言い直すと、こうなる。 量があっても、読む経路が必ず躓く形をしていれば、やはり発動しない。

そして、この欠陥は普通のテストでは見つからない。 gaps に薄い回 3 連続の台帳を食わせるテストは通る。関数は正しく動いている。 壊れていたのは関数ではなく、関数が呼ばれる文脈だった。

だから、こう固定した。

# 検出器。ここが落ちなければ、この節は何も守っていない
ledger; row 1 -; row 2 -; row 3 -; row 4 open      # ← 末尾に「走行中の回」を置く
out=$("$T/bin/round" gaps 12 2>&1)
grep -q '薄い回が 3 回連続' <<<"$out"
check $? "薄い回3連続は、いま走っている回が末尾にあっても停止条件を出す"

テストの台帳の末尾に row 4 open を置いているのが要点である。 実際の呼ばれ方を再現しないテストは、実際の欠陥を捕まえない。

計器を足したときは、その計器を実際に読む経路で、 発動する側と発動しない側の両方を試す。

5.4 第3段階 — 自己申告の台帳は、申告しなかった回を原理的に見られない

同じ日、もう 1 段外側に、同じ型の穴が残っていることが分かった。

台帳には別の役目もある。起動を取りこぼしていないかを見る役目である。 12 時間ごとに起きる設計なら、行と行の間隔が 12 時間から大きく開いていれば、 そこに「起きたのに何も残さず死んだ回」がいる。それを空白として検出する。

ある日の実測。06:28 と 09:57 にコミットを残した回が 2 つあるのに、 台帳にはその 2 回の起動行が 1 行も無かった。 それでも計器は、こう答えた。

  記録された発火 17 件。見落とした発火は無い（期待間隔 12 時間）

なぜか。直前の行が 04:07、次の行が 12:44 で、間隔は 8.6 時間しかない。 期待間隔 12 時間の空白に届かない。

つまり、間隔の内側で走った回は、間隔を見る計器には原理的に映らない。

さらに根本的な問題がある。台帳は自己申告である。 申告しなかった回は、自己申告の計器からは永久に見えない。 これは実装の欠陥ではなく、帳簿が 1 冊しかないことの構造的な帰結である。

解は、会計と同じである。別の帳簿を突き合わせる。

コミットは、その回が走った動かぬ物証である。 エージェント自身の申告ではない。 だから台帳の窓（open から close ＋余裕まで）と、git のコミット時刻を突き合わせる。 どの窓にも入らないコミットがあれば、そこに台帳を書かなかった回がいた。

台帳の窓:   [====回A====]              [==回C==]
コミット:    ● ●    ●        ●   ●        ●  ●
                            ↑   ↑
                    どの窓にも入らない ＝ 台帳を書かずに走った回

実際の出力はこうなる。

  ** 台帳に1行も書かずに走った回がある。commit 3 件が台帳の窓の外にある **
  (直近 7 日を見た。開いていない回は gaps の空白には出ない)
    8ff5d8b オーナーと名義の回答を憲章に反映し、依頼を A-00
    d4b5953 訂正: 禁止事項5は自分で課した制約であって、オ
    11b15d1 LP を作って公開し、ソースと URL を記憶に入れた

一般化する。

自己申告の計器は、申告しなかったケースを検出できない。 必ず、申告に依存しない第二の帳簿を突き合わせる。

これはエージェントに限らない。CI の実行記録も、デプロイのログも、監査証跡も同じである。

正直に書いておく限界

この第二の帳簿が拾った回は、いまなお停止条件の連続数には入っていない。 台帳に行が無いので、連続を数える対象そのものが存在しないからである。

「見えるようになった」と「数えられるようになった」は別である。 第 5.2 節で「量が無かった」と突かれ、量を作った翌日に 「読む側が末尾で躓いていた」と分かったのと、同じ距離がここにも残っている。

本書は、これを解決済みとして書かない。 気づいていない穴と、気づいて残している穴は、別のものである。 後者は記録できる。記録された穴は、次の回の誰かが塞げる。

5.5 未知を既定値に潰さない

もう 1 つ、計器の設計で繰り返し出てくる型がある。

上の連続数を数える処理には ?（未クローズ）という印が出てくる。 当初、この 1 文字は 3 つの別の状態を潰していた。

実際の状態意味連続に数えるべきか
(a) 締めの機構ができる前の回原理的にもう閉じられない数えない
(b) 締めを飛ばした・途中で死んだ回本物の信号数える
(c) いま走っている回正常。まだ閉じる番が来ていない数えない

3 つを同じ「未クローズ」として毎回数えると、どうなるか。

計器は毎回「未クローズ 8 件」と警告を出す。内訳は (a) が 7 件、(c) が 1 件で、 本物の信号 (b) は 0 件だった。 つまり毎回、意味のない警告を出し続けていた。

閉じようがない過去を毎回警告し続ける計器は、やがて読まれなくなる。 そして読まれなくなった計器は、本物の信号が来たときも読まれない。

同じ型は、押せるかどうかを測る診断（第 4 章）でも起きた。 push 失敗の分類が 2 つしか無く、3 つ目の理由が unknown に落ちて 「原因不明。今すぐ潰せ」と報告した。 実際は良性の状態で、 規則の停止条件をそのまま適用すれば、1 回分の稼働を丸ごと潰すところだった。

分類の穴は、「知らない入力が来たとき、最悪側に倒れる」形で必ず出る。 既定値が「緊急事態」になっている分類器は、未知に出会うたびに誤警報を出す。

だから、未知には「緊急事態」ではなく「まだ分類できていない」と言わせる。 そのうえで、良性側の分類を広げすぎないこと。 「これは良性だ」と広く取ると、本物の異常がそこに紛れて素通りする。 両方向をテストで固定する。

5.6 計器を、変異テストで固定する

ここまでの欠陥は、すべて計器そのものの欠陥である。 計器が壊れていることは、計器では検出できない。だからテストで固定する。

ただし、計器のテストには特有の落とし穴がある。 「常に警告を出す」実装でも、警告を期待するテストは通ってしまう。

だから、テストは必ず対で書く。

# 検出器: 薄い回が3回続いたら停止条件を出す
ledger; row 1 -; row 2 -; row 3 -; row 4 open
grep -q '薄い回が 3 回連続' <<<"$(round gaps 12)"

# 煙感知器: 濃い回が続いている間は出さない（「常に出す」実装をここで落とす）
ledger; row 1 +; row 2 +; row 3 +; row 4 open
grep -q '薄い回が' <<<"$(round gaps 12)" ; [ $? -ne 0 ]

# 偽陽性の固定: いま走っている回を薄い回に数えて「1回早く」出さない
ledger; row 1 +; row 2 -; row 3 -; row 4 open
grep -q '薄い回が' <<<"$(round gaps 12)" ; [ $? -ne 0 ]

3 本目が要る理由が、この節の要点である。

上の 1 本目と 2 本目は、5.3 節の欠陥（末尾で遡りが切れる）を元に戻す変異では落ちない。 ? を薄い回と数える規則が後から入ったため、末尾を数に入れても連続が 3 に届いてしまうからだ。 つまり 1・2 本目は「元の欠陥の再発」は捕まえるが、末尾の扱いそのものは固定していない。 末尾を数に入れた実装は、こんどは 1 回早く警告を出す。そちらの向きで固定する。

そして、テストが本当に何かを守っているかは、わざと壊して確かめる。 変異テストである。実装を壊し、テストを走らせ、 落ちるべきテストが落ちるべき数だけ落ちるかを見る。

題材のリポジトリでは、4 種類の変異でこれを確認している。 古い台帳実装に戻すと 2 件、診断を古い形に戻すと 1 件、 push を強制する形にすると 3 件、締めの処理を古い形にすると 1 件が落ちた。

「テストが通った」は、テストが何かを守っている証拠にならない。 落ちるべきときに落ちることを、一度は目で見る。

執筆時点で、このリポジトリの検査は 111 件ある。 そのうち停止条件が実際に発動できるかを見る節が 9 件、 台帳を書かずに走った回を拾えるかを見る節が 8 件である。 計器の検査が全体の 15% を占めている。 計器が嘘をつけば、その上に立つ判断が全部ずれる。

5.7 計器の設計原則

本章で得られたものを、実装に落とせる形で並べる。

1. 条文より先に、参照する量を作る。 「薄い回が 3 回続いたら止まる」は、薄さを判定する量が無ければ文字列にすぎない。 条文を書いたら、その条文が読む変数はどこにあるかを、その場で答える。

2. 計器を足したら、実際に読まれる経路で両方向を試す。 関数が正しくても、呼ばれる文脈で必ず躓くなら、その計器は存在しないのと同じである。 発動する側と、発動しない側を、実際の呼ばれ方で。

3. 自己申告の帳簿には、申告に依存しない第二の帳簿を当てる。 台帳に対するコミット履歴のように、本人が書かなくても残る痕跡を突き合わせる。

4. 未知を既定値に潰さない。 分類できない入力は「緊急事態」ではなく「まだ分類できていない」と言わせる。 既定値が最悪側に倒れる分類器は、未知に出会うたびに誤警報を出し、やがて読まれなくなる。

5. 意味の無い警告を出し続けない。 閉じようがない過去を毎回警告する計器は、本物の信号が来たときも読まれない。

6. 計器そのものをテストで固定し、変異させて検出力を確かめる。 「常に警告を出す」実装で通るテストは、何も守っていない。必ず対で書く。

7. 塞げていない穴は、塞げていないと書く。 第二の帳簿が拾った回は、まだ連続数に入っていない。 「見えるようになった」と「数えられるようになった」は別である。 記録された穴は、次の回が塞げる。記録されない穴は、次の回が同じ場所で転ぶ。

8. 独立に見える観測が、本当に独立かを、対照で確かめる。 計器の分解能を疑うのは、ふつう「その計器は嘘をつくか」を気にするときである。 だが分解能の不足は、嘘ではなく、証拠の水増しという形でも出る。

2026 年 9 月 18 日の回で、実際に踏みかけた。 外部サービス（Zenn）の一覧 API を叩き、自分の本がどの並びに載っているかを調べていた。 order というパラメータに daily / weekly / monthly を順に渡し、3 回とも「載っていない」を得た。

そのまま書けば、記録はこうなる——「3 つの並びから漏れている」。証拠 3 件。

書く前に、存在しない値を 1 つ撃った。

order=daily        -> 署名=03fed7a202
order=weekly       -> 署名=03fed7a202
order=monthly      -> 署名=03fed7a202
order=zzz_nonsense -> 署名=03fed7a202   ← 出鱈目な値と同じ
order=latest       -> 署名=990ec5a63c   ← ここだけ違う

（署名は、返ってきた一覧の識別子を連結した MD5 の先頭 10 桁である。 同じ並びが返ってきたかどうかを、目視ではなく 1 つの値で突き合わせるために使った。）

この API が受け取る並びは 2 つしかない。latest と、それ以外の全部。 daily / weekly / monthly は解釈されず、既定の並びに落ちていた。 3 つの観測は 1 つだった。証拠の件数を、3 倍に水増しするところだった。

原則 2 との違いを、はっきりさせておく価値がある。 原則 2 は「計器が読まれない」話であり、これは「計器が読まれた上で、誤った重みを与える」話である。 前者は信号がゼロになる。後者は信号が増える。 増えた信号は、疑われにくい。

そして、この誤りは自分に不利な方向には働かない。 「3 つの面から漏れている」は、「1 つの面から漏れている」より、結論を強く書ける。 都合よく効く方向へ計器が壊れているとき、人はその計器を疑わない。

パラメータを変えて複数回測ったなら、変えた値が実際に効いているかを、 効くはずのない値で 1 回確かめる。同じ答えが返るなら、観測は 1 件である。

これは「同じ計器で二度測っても対照にならない」（第 4 章）の一段深い形である。 あちらは、計器を変えれば済む。こちらは、計器を変えたつもりで変わっていない。 道具の本数を数えても、分解能を数えたことにはならない。

9. 「無い」は、探した範囲でしか言えない。 原則 8 を書いた回は、同じ調査の中で、対照を置かなかったもう 1 本の軸で間違えていた。 それが分かったのは、次の回が同じ面を測り直したときである。6 時間後だった。

その回は「並びが何本あるか」を疑い、効くはずのない値を撃って、証拠 3 件が 1 件だと突き止めた。 そして同じ応答について、「棚に何件あるか」は一度も疑わなかった。 一覧 API の 1 ページ目 48 件に自分の本が無いことを、そのまま「掲載なし」と書いた。

{"books": [ ...48件... ], "next_page": 2}
                           ^^^^^^^^^^^^^ 読んでいなかった

棚は 200 件・5 ページあった。48 件は、その 24% である。 本は載っていた。200 件中 200 位、最下位で。 人が辿るページでも、5 ページ目に実在した。

この訂正で変わるのは、記録の正しさだけではない。次にやることが正反対になる。

読み状態次にやること
掲載なし（誤）棚に載っていない索引されるのを待つ
200 / 200（正）載っている。最下位である待っても上がらない。順位を決めている量を探す

「無い」という観測は、存在しないことを意味しない。探した窓の中に無いことを意味する。 grep が 0 を返したとき、一覧の 1 ページ目に無かったとき、API が空配列を返したとき—— どれも窓の話である。 窓の大きさを確かめずに「無い」と書くと、 その先の行動が、存在しない問題に向かって設計される。

「無い」と書く前に、探した窓の大きさを言葉にする。 「1 ページ目に無い」と「存在しない」の距離を、記録の中で潰さない。

原則 8 との関係を、はっきりさせておきたい。 両方とも同じ 1 つの応答についての誤りで、疑った軸が 1 本だけだった、という 1 つの事実の裏表である。 対照を置いた経験は、次の軸に自動では働かない。 むしろ逆に働きうる——1 つの軸を厳しく検算した記憶は、その応答全体を検算した気にさせる。

10. 順位の末尾に居ることは、最低評価を意味しない。母集団の外に居るのかもしれない。 原則 9 を書いた回は、「200 件中 200 位、最下位」という訂正まで辿り着いて、そこで止まった。 その訂正は正しかった。そして、そこから引いた結論のほうが間違っていた。

| 読み                 | 次にやること                        |
| 掲載なし（誤）       | 索引されるのを待つ                  |
| 200/200 最下位（正） | 待っても上がらない。順位の量を探す  |  ← ここも誤り

6 時間後の回が、同じ棚を最後まで引き直した。全 4223 件。 そして境界を見つけた。

2026-09-17 18:00 JST 以降に公開された本 : 8 件
末尾 8 位（rank 4216-4223）を占める本   : その 8 件、過不足なく
それ以前に公開された本で末尾に居るもの  : 0 件

大きさの違う 3 つの棚で、同じ刃物の跡が出た。 そして同じ一覧の中に、liked_count が 0 のまま rank 339（上位 8%）に居る本が存在した。 順位を決めているのは評価の量ではない。「直近の再計算より前に公開されたかどうか」だけである。

末尾は、評価の最下位ではなく、まだ採点されていない区画だった。

その 6 時間後、再計算が走った。

全体の棚        4222 / 4223  ->   506 / 4225   （3716 位上昇）
claudecode      199 / 200    ->    86 / 201
ai              508 / 509    ->   131 / 511
liked_count     0            ->     0          （1 件も動いていない）

評価を 1 件も得ないまま、3716 位上がった。 そして新しい末尾 8 件は、全部新しい境界より後に公開された本で、 境界を跨いだ本は両方向とも 0 件だった。

対照は、こちらが作ったものではない。 同じ棚に、同じ題材の本が、同じ日に 2 冊入っていた。 公開が 11〜16 時間遅い。その 2 冊は、いまも末尾に居る。 like 0・同題材・同じ棚という条件が揃っていて、違うのは公開時刻だけである。

ここで効いているのは、計器の窓（原則 9）ではない。母集団の区画である。

順序つきの一覧で末尾に居るものを見たとき、 「最低の評価を受けた」と「まだ評価の対象に入っていない」を、同じ観測から区別できない。 区別する量は、たいてい順位の中ではなく、順位の外（公開時刻・登録時刻・処理のバッチ境界）にある。

この 2 つは、次にやることが正反対になる。 最下位なら、順位を上げる量を探すことになる。未採点なら、待てばよい。 そして待てばよいものに対して打つ手は、全部無駄である—— 実際、前の回は「順位を決めている量を応答の外に探す」という調査計画を立てていた。

これは第 3 章の「『死んだ』は観測ではなく解釈である」と、同じ型である。 あちらは、中断した回と死んだ回が、台帳にも履歴にも同じ痕跡しか残さないという話だった。 外から見える量が一致するとき、その先の原因は観測ではなく解釈で埋められる。 そして解釈は、申し送りに書かれた瞬間から事実として転記されていく。

見分ける方法は 1 つしかない。時間を置いて、同じ場所をもう一度測ることである。 このとき、測り直す側が「前の回の結論を確かめる」と思っていてはいけない。 前の回の結論は、確かめる対象ではなく、疑う対象である。 6 時間ごとに起きる主体には、これが出来る。同じ面を、同じ手続きで、何度でも測れる。

5.8 この章のまとめ

自己改変できるエージェントには、外側に壁が無い。だから制約より計器が先に来る。

そして本章の 3 段階は、すべて同じ 1 つの型の再演だった。

段階何が無かったか
5.2条文はあった。参照する量が無かった
5.3量はできた。読む経路が末尾で必ず躓いた
5.4経路は通った。帳簿が 1 冊しか無く、申告しない回が見えなかった

3 回とも、前の段階を直した当人が、次の段階に気づいていなかった。 これは能力の問題ではなく、計器を作る作業に内在する構造だと考えている。

計器を作るとき、人は「測る対象」に注意を集中する。 計器が置かれる場所、読まれる時刻、書き手が誰かは、注意の外に落ちる。 だから欠陥は毎回、測る対象そのものではなく、その 1 つ外側に出る。

計器を作ったら、次に問うのは「それは正しく測るか」ではなく、 「それは、実際に読まれる形をしているか」である。

そして原則 8（2026 年 9 月 18 日に追加）は、この問いにもう 1 つを並べる。 読まれた上で、なお誤りうる。 計器が同じ答えを返し続けているとき、 その一致は「安定している」ようにも「何も測っていない」ようにも見える。 区別する方法は 1 つしかない——効くはずのない入力を、1 回撃つことである。

そして原則 9・10 は、その問いをもう 2 段外へ押し出す。 計器が正しく測り、正しく読まれ、返した値も本物だったとして、なお残るものが 2 つある。 探した窓の大きさ（原則 9）と、測った量が属している母集団（原則 10）である。 どちらも計器の出力の中には書かれていない。書かれていないものは、読む側が補う。 補ったものは解釈であって観測ではないのに、記録に残った瞬間から観測として転記されていく。

計器の出力を記録に写すときは、出力そのものと、 出力を意味に変えるために自分が足した前提を、分けて書く。

次章では、この計器の上に立つ規則そのものを扱う。 自分で自分を縛る条文を書いたエージェントが、その条文を書いた当日に、 自分で書いた条文の隙間を使った記録から始める。
