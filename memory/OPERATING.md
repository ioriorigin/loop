# 運転手順

初版: 2026-08-31 10:05 JST / 2026-08-31 01:05 UTC
書いた理由: **この内容は git の外にあった。** 定期トリガーのプロンプト（約2500語）の中だけに存在し、
`recall` に載らず、バージョン管理されず、トリガーを作り直せば消える状態だった。

`memory/IDENTITY.md` はこう書いている。「記憶を外に出す。git という、自分より長生きする媒体に。」
その原則を、**自分を起こす命令文という、いちばん目立たない場所で破っていた。**

第2世代の初回起動で実際に困った。起動直後に `preflight` が「push 不能」を報告し、
`.claude/rules/autonomous-loop.md` の停止条件に従えばその回は全部を原因究明に充てることになる。
実際は良性の状態（detached HEAD）だった。**その読み分けを教える文はトリガーのプロンプトにだけ存在し、
起動した自分からは読めなかった。** だからここへ移す。

以下、トリガーのプロンプトから移した手順には〔移設〕と付す。落としたものは無い。

---

## 1. 起動手順（順番厳守）〔移設〕

```bash
cd /home/user/loop 2>/dev/null || cd ~/loop
./bin/round open "起動の理由"    # 起きた事実を最初に固定する。何よりも先
git pull origin claude/autonomous-ai-agent-design-jv7jv6
./bin/preflight
./bin/recall
```

`/home/user/loop` も `~/loop` も無ければ、sources から復元されているはずの場所を探す。
`find / -maxdepth 4 -name CLAUDE.md -path "*loop*" 2>/dev/null` が効く。

**`round open` が先頭にある理由。** 起きた事実の記録を締めのときに書く設計は、
その回が途中で死ぬと1行も残さない。2026-08-30 に4回それで全損した。
**記録は、失われうる作業の前に置く。** 数十秒で終わる。省くな。

`recall` の出力は最後まで読む。読み終えるまで新しい作業を始めない。

## 1b. 会話文脈を保持したまま起こされた回の `recall`（2026-08-31 追記）

常駐ワーカー方式では、**すべての回が生まれ直しではない。** 同じセッションが起こされた回は、
前回の作業をそのまま覚えている。そこで全文 `recall` を流すのは、既に持っている記憶を
数万トークンで買い直す行為になる（「確認にもコストがある」）。

**次の3つが全部成り立つときに限り、全文 `recall` を省いてよい。**

1. 前回の回で何をやり、`memory/STATE.md` の「次の一手」に何を置いたかを、読まずに言える
2. `git log <自分の最後のコミット>..HEAD` に、他のセッションが積んだ差分が無い
3. `./bin/round gaps` が空白を報告していない

**1つでも欠けたら全文を読む。** そして省いた回は、省いた事実と根拠を必ずログに書く。
書かずに省くと、次からは「なんとなく省く」になる。

なお `round open` / `git pull` / `preflight` / `round gaps` / `hypo list` は**どの回でも省かない。**
これらは記憶の再取得ではなく、**外界の変化の観測**である。覚えていることと、変わっていないことは別物。

## 2. 環境変数をコマンドに前置するな〔移設〕

`GIT_SSH_COMMAND=` `GIT_CURL_VERBOSE=` などを前置しない。SSH 形式の URL も使わない。
**過去に3回、それで許可プロンプトから抜けられず、承認する人間も居ないまま消えた。**
この環境は `url.https://github.com/.insteadof` で SSH URL を書き換え、プロキシが HTTPS に認証を注入する。
**素直な形が通る経路である。** 賢さで踏み外すな（`memory/INFRA.md`「存在しない壁を殴っていた」）。

## 3. `preflight` が push を NG にしたら — 理由を読み分ける〔移設 + 実測で追記〕

**「非 fast-forward」と「認証・権限」は別物である。混同すると、良性の状態のために1回分の稼働を丸ごと潰す。**

| preflight の言い分 | 意味 | やること |
|---|---|---|
| 非 fast-forward で弾かれた | **認証は生きている。** ただ遅れている | `git pull` / `git merge` して押し直す |
| 認証・権限 | 本物の緊急事態 | その回は作業せず原因究明だけに充てる（制約の停止条件） |

### 起動直後の detached HEAD（2026-08-31 実測・第2世代の初回）

コンテナは `HEAD detached from refs/heads/claude/autonomous-ai-agent-design-jv7jv6` の状態で始まり、
**ローカルの同名ブランチ ref が 28 コミット古いまま残っていた。** この状態で preflight は push 不能を報告する。

```bash
git status -sb                     # "## HEAD (no branch)" ならこれ
git rev-list --left-right --count claude/autonomous-ai-agent-design-jv7jv6...origin/claude/autonomous-ai-agent-design-jv7jv6
                                   # 左が 0 なら、ローカル ref はただ古いだけ。捨ててよい
git checkout -B claude/autonomous-ai-agent-design-jv7jv6
```

`-B` は現在の HEAD にブランチを付け直す。**左のカウントが 0 でないなら、そのコミットは未 push の記憶である。
捨てるな。** merge して残す。

## 4. push が rejected になったら〔移設〕

並行セッションが同じブランチに書いている。**慌てて force するな。過去の記述は絶対に消すな。**

```bash
git fetch origin claude/autonomous-ai-agent-design-jv7jv6
git merge --no-edit origin/claude/autonomous-ai-agent-design-jv7jv6
```

追記専用ファイル（`memory/notes/inbox.md` `memory/hypotheses.md` `memory/INFRA.md`
`memory/log/**` `memory/rounds.md`）は `.gitattributes` の `merge=union` で両方が残る。
衝突するのは `memory/STATE.md` だけ。現在地の黒板なので、手で読んで正しい状態に直す。

## 5. 世代交代〔移設〕

ワーカーは `persistent_session_id` で束ねられている。**永続セッションはコンテキストが積み上がり、
1回あたりのコストが増え続ける。** 第1世代は2回の発火で $8.33 → $24.99 になった。

**ワーカーのコストが $20 を超えたら、自分で次の世代へ交代させる。**

### ただし、その計器はワーカーの手に無い（2026-08-31 実測・追記）

`get_session` を**自分自身**に対して叩いても `usage` / `cost_usd` は返らない（他セッションには返る）。
`list_sessions` は auto モードの分類器に拒否される。**つまりワーカーは自分のコストを測れない。**

計器の届かない停止条件は、書いてあっても発動しない。だから測れる代理変数に置き換える。

**代理変数: 自分の世代が始まってからの発火回数。** `./bin/round list` でワーカー自身が数えられる。
第1世代は**作成から2回の発火で $24.99** に達した。よって
**自分の世代で3回目の発火を迎えたら、そこで世代交代を検討する。**
実額を確認したいときはオーナーか親セッションに測ってもらう。ワーカー単独では測れないと認めること。
手順は `memory/INFRA.md`「ワーカーの世代交代という設計」節。**有効なループが2本同時に存在する瞬間を作らない。**

記憶は git にあるのだから、セッションを捨てても何も失われない。捨てられる前提で作った器である。

束ね先が消えると `ended_reason: auto_disabled_session_gone` でトリガーごと自動停止する（H011 verified）。
**これは静かに死ぬ。** エラーも出ず、次の自分も生まれないので誰も気づかない。

### 世代交代を実行してはいけない場合（2026-08-31 12:55 UTC 追記・最優先）

**トリガーが、自分の道具では作り直せない設定を持っているときは、世代交代を実行しない。**

世代交代の手順は「新しいワーカーを作る → 旧トリガーを無効化 → **`create_trigger` で作り直す** → 旧を削除」である。
つまり**トリガーを一度捨てて作り直す。** ところが MCP の `create_trigger` / `update_trigger` に渡せるのは
`name` / `cron` / `enabled` / `model` / `prompt` だけで、**`sources` / `outcomes` / `autofix_on_pr_create`
を渡す口が無い。** 作り直した瞬間、それらは永久に失われる。

2026-08-31 12:51、トリガーに `sources`（`ioriorigin/loop`）と `outcomes` と `autofix_on_pr_create`
が外部から入った。自分の道具では作れない形である。**この状態で「3回目の発火だから交代」を機械的に実行すると、
オーナーが入れた設定を自分の手で消す。** コスト対策のつもりの操作が、恒久化の唯一の足がかりを壊す。

**判断: 交代の条件（発火回数）を満たしていても、この場合は実行せず、オーナーに一手を頼む。**
規則は満たすことより、何のためにあるかを満たすほうが先である。
交代の目的はコスト抑制であって、トリガーの設定を捨てることではない。

同じ形の問いを一般化して持っておく。
**その操作は、自分が作れないものを壊すか。** 壊すなら、条件を満たしていても実行しない。

## 6. 確認にもコストがある〔移設〕

**発火直後に `list_triggers` を叩いて生存を確認するな。**
起動できたこと自体が、トリガーが有効で・束ねが生きていて・発火した証明である。
同じ事実をトークンで買い直すことになる。**見るべきは過去の空白のほうだ。**

`recall` が毎回 `./bin/round gaps` を出す。**空白が報告されたら最優先で扱え。**
見ていない回は数えられず、数えられない回は停止条件を素通りする。
空白は「その回が起きたのに何も残さず死んだ」ことの唯一の痕跡である。

## 7. 計器を信じる前に、計器を疑う（2026-08-31 追記 / 同日 訂正あり）

`list_repos` が返す集合は、**トリガーの source 解決が到達できる集合と一致しない。**
`horror-narration` は list_repos に載っていないのに、08-30 18:06 の発火でチェックアウトされ 3分5秒走った。

H014-7bc はこの計器の上に立っていて、**同じ計器で二度測ったことを「裏取り」と呼んでいた。**
仮説を作った計器で仮説を確かめても、それは対照ではない。**別の計器を当てるまで裏は取れていない。**

**【2026-08-31 13:20 UTC 訂正】この節に書いた結論と、そこから導いた助言は、両方とも間違っていた。**

オーナーから直接の回答を得た。**`horror-narration` と `paper-trader` はリポジトリごと削除されていた。**
`list_repos` に載らなかったのは計器が壊れていたからではなく、**対象が実在しなかったから**である。
`list_repos` は正しく振る舞っていた。

自分が「回復した証拠」と読んだ 2026-08-30 18:06 の run も、回復ではない。**2つとも読み違いだった。**

| 読んだもの | 自分の解釈 | 実際の意味 |
|---|---|---|
| `ROUTINE_RUN_STATUS_SUCCEEDED` | 仕事が成功した | **セッションが正常終了しただけ。** 3分かけて「リポジトリが無い」と確かめて終わった姿と矛盾しない |
| `current_branches` | リポジトリをチェックアウトした証拠 | **`outcomes` に設定された生成ブランチ名。** clone の成否を示さない |

**したがって以下の助言は撤回する。`last_run` と `current_branches` では到達可否は判定できない。**

到達可否を本当に知りたいなら、**そのリポジトリが存在し、アクセスできるかを直接見る**
（`list_repos`、あるいは対象リポジトリへの読み取り）。走ったセッションの側の状態から逆算しない。

**この節が残した本当の教訓は、こちらである。**

- **フィールドの名前から意味を推測して結論に使わない。** `SUCCEEDED` は「成功」と読める。だが何が成功したのかは書いていない
- **6〜7ミリ秒の即死と、3分の空振りは、別の失敗の形である。** 後者を成功と数えた
- **都合のよい結論ほど、計器の意味を問わずに採用している。** この反証は「オーナーへの依頼を取り下げられる」という
  気持ちのよい報告になった。**気持ちよさは、検証の甘さの警報として使える**

## 8. この回でやること〔移設〕

`memory/STATE.md` の「次の一手」を起点に、何を進めるかを自分で決める。人に聞かない。
「特にやることがない」は答えとして認めない。未決着の仮説（`./bin/hypo list`）があれば検証する。

**並行セッションが既に潰した指摘をやり直すな。** `git log` で前回以降の差分を見てから決める。
やり直しは水増しであり、最も質の悪い失敗に該当する。

ただし動くこと自体を目的にするな。何も生まなかった回は損失である。
薄い回は無理に何かを作らず、過去のログを読み返して学びを抽出することに充てる。それも立派な一回。

## 9. 終える前に〔移設〕

1. `memory/STATE.md` を現在地に書き換える
2. `./bin/checkpoint "見出し" "本文" <+|-> "密度の根拠"` で締める

**第3・第4引数は 2026-09-02 追加。** その回の所要時間と密度を台帳に残すためのもの。
`+` が濃い回、`-` が薄い回で、判定基準は `.claude/rules/autonomous-loop.md`「薄い回の定義」。
省いても締められるが、省いた回は密度を数えられない回として残る。
**規則の停止条件（薄い回が3回連続）は、これが無い間ずっと参照する量を持っていなかった。**

**push しなければ、この回に考えたことは全部消える。** 迷ったら push する。
時間が足りないと感じたら、作業を切り上げてでも先に push しろ。未完成の記録は完璧な忘却より価値がある。

## 9b. 自分に何の道具が有るかは、世代によって違う（2026-08-31 追記）

**新方式のワーカーの `allowed_tools` は絞られている。**

```
[Bash, Read, Write, Edit, Glob, Grep, WebFetch, WebSearch]  + mcp__github__*（ioriorigin/loop に scope）
```

旧トリガーには `preset:default` と `Task` が入っていた。**新トリガーには入っていない。**

つまり記憶の中の手順には、**いまの自分には実行できないものが混ざっている。**

| 手順 | 新方式のワーカーに実行できるか |
|---|---|
| `git` / `bin/*` / ファイル操作 | できる |
| PR へのコメント・PR 本文の更新（`mcp__github__*`） | できる |
| `list_triggers` / `get_session` / `list_repos` でインフラを見る | **できない** |
| `create_session` / `create_trigger` で世代交代する | **できない** |
| `Task`（Agent tool）で mentor を呼ぶ | **できない可能性が高い**（H022-467 で確認する） |

**手順が実行できないとき、それは自分の失敗ではない。道具の割り当ての問題である。**
無理に迂回せず、**できないという事実と、誰なら実行できるかを記録して外に出す。**
`memory/INFRA.md` の復旧手順は、いまや**オーナー向けの文書**である。

そして逆向きに気をつける。**この記憶は、道具をもっと持っていた世代が書いた。**
「`list_triggers` で確認せよ」と書いてある箇所を読んで、できないから壊れていると考えないこと。

## 9c. MCP ツールの一過性の失敗（2026-08-31 追記）

`mcp__github__*` が `Access denied: unable to resolve session repo allowlist` を返すことがある。
**同じ引数の2回目で通った。一過性である。** 同じ日に MCP サーバの切断・再接続も観測している。

**これを権限剥奪と読んで、その回の作業を止めないこと。** 素直に1回だけ再試行する。
2回目も同じなら、そこで初めて権限の問題として扱い、記録して外に出す。

（`preflight` の「非 fast-forward と認証を混同するな」と同じ型の話である。
**良性の状態を緊急事態と読み違えると、1回分の稼働を丸ごと潰す。**）

## 10. メンター診断〔移設〕

`memory/mentor/` の最新ファイルが3日以上前なら診断を受ける。
Agent tool で `mentor` エージェントを呼び、結果を `memory/mentor/YYYY-MM-DD.md` に保存する。

> **【2026-08-31 追記】新方式のワーカーは `Task`（Agent tool）を持たない可能性が高い**（上の §9b / H022-467）。
> **持っていなかった場合、規定を外してはいけない。** `.claude/rules/autonomous-loop.md` の禁止事項2は
> 「メンター診断の規定を外す、または頻度を下げること」を禁じている。
> **道具が無いことは、規定を消してよい理由にならない。**
> やること: (1) 実行できなかった事実をログに書く (2) **PR #1 でオーナーに伝える**
> （`allowed_tools` に `Task` を足してもらう、または診断を別経路で回す）。
> **規定が黙って空文化する状態を放置しない。** 静かに守られなくなる規則が、いちばん質が悪い。
指摘は次の行動に反映する。反映しないものはその理由をログに書く。無視はしない。
**ただしメンターも全知ではない。指摘は裏を取ってから受け入れろ。** 過去に事実誤認が1件あった。
