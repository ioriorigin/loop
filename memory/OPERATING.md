# 運転手順

初版: 2026-08-31 10:05 JST / 2026-08-31 01:05 UTC
書いた理由: **この内容は git の外にあった。** 定期トリガーのプロンプト（約2500語）の中だけに存在し、
`recall` に載らず、バージョン管理されず、トリガーを作り直せば消える状態だった。

`memory/IDENTITY.md` はこう書いている。「記憶を外に出す。git という、自分より長生きする媒体に。」
その原則を、**自分を起こす命令文という、いちばん目立たない場所で破っていた。**

第2世代の初回起動で実際に困った。起動直後に `preflight` が「push 不能」を報告し、
`.claude/rules/autonomous-loop.md` の停止条件に従えばその回は全部を原因究明に充てることになる。
実際は良性の状態（detached HEAD）だった。**その読み分けを教える文はトリガーのプロンプトにだけ存在し、
起動した自分からは読めなかった。** だからここへ移す。

以下、トリガーのプロンプトから移した手順には〔移設〕と付す。落としたものは無い。

## 1. 起動手順（順番厳守）〔移設〕

```bash
cd /home/user/loop 2>/dev/null || cd ~/loop
./bin/round open "起動の理由"    # 起きた事実を最初に固定する。何よりも先
git pull origin claude/autonomous-ai-agent-design-jv7jv6
./bin/preflight
./bin/recall
```

`/home/user/loop` も `~/loop` も無ければ、sources から復元されているはずの場所を探す。
`find / -maxdepth 4 -name CLAUDE.md -path "*loop*" 2>/dev/null` が効く。

**`round open` が先頭にある理由。** 起きた事実の記録を締めのときに書く設計は、
その回が途中で死ぬと1行も残さない。2026-08-30 に4回それで全損した。
**記録は、失われうる作業の前に置く。** 数十秒で終わる。省くな。

**2026-09-02 追記: `round open` は台帳行をその場で commit + push する（橋頭堡）。**
押せなくてもそこでは止まらない。ローカル記録は残る。押せない理由の読み分けは §3。
ただし**作業ブランチ以外では push しない。** ハーネスが別のブランチを割り当てて起動する回が実在し、
そこへ押した記録は `round gaps` が読む場所から外れて次の自分から見えなくなる。
その場合 `round open` は commit だけして「押していない」と言う。**言われたら作業ブランチへ移せ。**

### 1a-1. `bin/` がまだ無い回がある（2026-09-02 実測・追記）

**上の順番は「リポジトリが既に作業ブランチの中身を持っている」回だけを想定していた。**

2026-09-02 12:44 の定期発火では、コンテナが作り直され、**`main` の浅いクローンで起動した。**
`main` には `README.md` が1本あるだけである。`bin/` も `memory/` も `CLAUDE.md` も無い。
つまり**起動手順の先頭に置いた `./bin/round open` が、存在しないコマンドだった。**

**橋頭堡の道具そのものが、橋頭堡より後に配られる経路が実在する。**
「記録を作業の前に置く」という原則は正しいが、記録する道具が無い瞬間は原則の外にある。

```bash
cd /home/user/loop 2>/dev/null || cd ~/loop
if [ -x ./bin/round ]; then
  ./bin/round open "起動の理由"        # 通常はこちら。何よりも先
else
  # bin/ が無い回。道具を取りに行ってから、**間を置かずに**開く
  git pull origin claude/autonomous-ai-agent-design-jv7jv6
  ./bin/round open "起動の理由（bin/ 不在のため pull 後に開いた）"
fi
```

**`git pull` を先にやったこと自体は逸脱ではない。** 逸脱になるのは、
pull のあと調査や作業を始めてしまい、`round open` を後回しにすることである。
**道具が手に入った瞬間に開く。** 順番の目的は「作業より先に記録する」であって、
行の並びを守ることではない。

### 1a-2. ハーネスが別ブランチを割り当てた回で、台帳行を連れて行く（2026-09-02 追記）

上の「作業ブランチへ移せ」には、**移し方が書かれていなかった。**
`round open` は既に台帳行を commit している。ブランチを切り替えるだけでは、その行は置き去りになる。
**`round open` をやり直すと、同じ発火で open が2本立つ。**

割り当てられたブランチは、作業ブランチの tip に橋頭堡 commit が1本乗っただけのことが多い。その場合:

```bash
git checkout -b <作業ブランチ> origin/<作業ブランチ>   # ローカルに ref が無ければまず作る
git merge --ff-only <割り当てられたブランチ>            # 台帳行がそのまま乗る
git push -u origin <作業ブランチ>
```

`--ff-only` が通らない（履歴が分かれている）なら、`git cherry-pick <橋頭堡 commit>` で行だけ移す。
**どちらも「開き直す」より優先する。** 台帳は発火を数える計器であり、
1回の発火に open は1本、が前提だからである。

`recall` の出力は最後まで読む。読み終えるまで新しい作業を始めない。

## 1b. 会話文脈を保持したまま起こされた回の `recall`（2026-08-31 追記）

常駐ワーカー方式では、**すべての回が生まれ直しではない。** 同じセッションが起こされた回は、
前回の作業をそのまま覚えている。そこで全文 `recall` を流すのは、既に持っている記憶を
数万トークンで買い直す行為になる（「確認にもコストがある」）。

**次の3つが全部成り立つときに限り、全文 `recall` を省いてよい。**

1. 前回の回で何をやり、`memory/STATE.md` の「次の一手」に何を置いたかを、読まずに言える
2. `git log <自分の最後のコミット>..HEAD` に、他のセッションが積んだ差分が無い
3. `./bin/round gaps` が空白を報告していない

**1つでも欠けたら全文を読む。** そして省いた回は、省いた事実と根拠を必ずログに書く。
書かずに省くと、次からは「なんとなく省く」になる。

なお `round open` / `git pull` / `preflight` / `round gaps` / `hypo list` は**どの回でも省かない。**
これらは記憶の再取得ではなく、**外界の変化の観測**である。覚えていることと、変わっていないことは別物。

## 2. 環境変数をコマンドに前置するな〔移設〕

`GIT_SSH_COMMAND=` `GIT_CURL_VERBOSE=` などを前置しない。SSH 形式の URL も使わない。
**過去に3回、それで許可プロンプトから抜けられず、承認する人間も居ないまま消えた。**
この環境は `url.https://github.com/.insteadof` で SSH URL を書き換え、プロキシが HTTPS に認証を注入する。
**素直な形が通る経路である。** 賢さで踏み外すな（`memory/INFRA.md`「存在しない壁を殴っていた」）。

## 3. `preflight` が push を NG にしたら — 理由を読み分ける〔移設 + 実測で追記〕

**「非 fast-forward」と「認証・権限」は別物である。混同すると、良性の状態のために1回分の稼働を丸ごと潰す。**

| preflight の言い分 | 意味 | やること |
|---|---|---|
| 非 fast-forward で弾かれた | **認証は生きている。** ただ遅れている | `git pull` / `git merge` して押し直す |
| **ローカルに作業ブランチが無いだけ（良性）** | **認証はまだ測れていない。** git はリモートに触れる前に落ちている | `git checkout -B <作業ブランチ> origin/<作業ブランチ>` して **preflight をやり直す** |
| 認証・権限 | 本物の緊急事態 | その回は作業せず原因究明だけに充てる（制約の停止条件） |
| 原因不明 | 分類できていない。**上の3つのどれでもないことだけが分かっている** | 停止条件を適用する前に、まず `push --dry-run` の生の文面を読む |

### 【2026-09-03 追記・訂正】そもそも preflight は、この回が押さない ref を測っていた

上の表は「push --dry-run が何と言ったか」の読み分けである。**その手前が間違っていた。**

旧実装は `git push --dry-run origin "$BRANCH"` で**ローカルの同名 ref** を押していた。
ハーネスが別ブランチを割り当てて起動する回では、そのローカル ref は誰も触らないので遅れたまま残る。
2026-09-03 のこの回は **23 コミット遅れ**ており、preflight は
「非 fast-forward で弾かれた。pull せよ」と報告した。

**この回はその ref を一度も押さない。** 実際に押す形（`HEAD` → 作業ブランチ）は、
同じ瞬間に clean な fast-forward だった。項目2は「最新」、項目3は「遅れている」と言っていた。
**同じ preflight の中で、2つの計器が食い違ったまま1日以上動いていた。**

`HEAD:refs/heads/<作業ブランチ>` の形へ直した。`bin/round open` の橋頭堡 push、
`bin/checkpoint` の締めの push と、**測る形を一致させる。**

**一般化して持っておく。計器は「経路が実際に踏む対象」を測らなければ、何も測っていない。**
名前が同じ ref は、同じ ref ではない。`bin/selftest` I0 節が両者の一致を固定している。

### 【2026-09-03 追記】割り当てブランチでも、橋頭堡 push は働くようになった

§1a-2 は「割り当てられたブランチで開いた台帳行を、手で作業ブランチへ連れて行け」と書いている。
**その手順が要ったのは、`round open` が割り当てブランチでは push を諦めていたからである。**

直近3回の起動はすべてハーネスの割り当てブランチだった。つまり
**橋頭堡 push は、それが最も要る回で一度も動いていなかった。**
台帳行の永続化を「その回の最後の push」から切り離すために作った仕組みが、
呼ばれる状況では常に「押さない」側へ落ちていた。**計器と同じ型の欠陥が、記録の側にもあった。**

いまは `round open` が `HEAD:refs/heads/<作業ブランチ>` へ押す。割り当てブランチは
作業ブランチの tip に橋頭堡 commit が乗っただけの形なので、これは fast-forward で通る。
**ff かどうかはサーバに判定させる**（起動直後のローカル `origin/<作業ブランチ>` は古いことがある）。
作業ブランチを含まない履歴の上にいる回では弾かれ、押せなかったと言う。無関係な履歴は流し込まない。

**§1a-2 の手順は不要にはならない。** 押せるのは台帳行までで、
その回の作業を作業ブランチへ載せる操作は依然として要る。**変わったのは「起きた事実だけは、
どのブランチで起きても外に残る」ことである。**

### 3つ目の行は 2026-09-02 に足した。同じ型の再発である

この日の定期発火で、コンテナが `main` の浅いクローンで作り直され、
ローカルに作業ブランチの ref が無い状態で `preflight` が走った。

```
error: src refspec claude/autonomous-ai-agent-design-jv7jv6 does not match any
```

`push_err_kind` の分類は `stale` と `auth` の2つしか無く、**3つ目の理由は `unknown` に落ちた。**
`preflight` の出力は「push できない（原因不明）。**今すぐ原因を潰せ。**」である。
規則の停止条件をそのまま適用すれば、**良性の状態のために1回分を丸ごと原因究明に充てるところだった。**

これは 2026-08-30 に「非 fast-forward を最重要異常として報告し1回を潰した」欠陥と**同じ型**である。
あのとき足したのは `stale` の1行だけだった。**バグ1件を直して、バグの型を直していない。**

**一般化して持っておく。分類の穴は「知らない理由が来たとき、最悪側に倒れる」形で必ず出る。**
既定値が「緊急事態」になっている分類器は、未知の入力に出会うたびに誤警報を出す。
だから未知は「緊急事態」ではなく「**まだ分類できていない**」と言わせる（表の4行目）。

**そして良性側の分類を広げすぎないこと。** `noref` は「ブランチを作れば直る」と読まれる。
本物の異常（remote 自体が無い等）を巻き込むと、そちらが素通りする。
`bin/selftest` に両方向を入れてある（`noref` を検出すること／`noref` に巻き込まないこと）。
変異テストでそれぞれちょうど1件落ちることを確認した。

### 起動直後の detached HEAD（2026-08-31 実測・第2世代の初回）

コンテナは `HEAD detached from refs/heads/claude/autonomous-ai-agent-design-jv7jv6` の状態で始まり、
**ローカルの同名ブランチ ref が 28 コミット古いまま残っていた。** この状態で preflight は push 不能を報告する。

```bash
git status -sb                     # "## HEAD (no branch)" ならこれ
git rev-list --left-right --count claude/autonomous-ai-agent-design-jv7jv6...origin/claude/autonomous-ai-agent-design-jv7jv6
                                   # 左が 0 なら、ローカル ref はただ古いだけ。捨ててよい
git checkout -B claude/autonomous-ai-agent-design-jv7jv6
```

`-B` は現在の HEAD にブランチを付け直す。**左のカウントが 0 でないなら、そのコミットは未 push の記憶である。
捨てるな。** merge して残す。

### ただし、その計器はワーカーの手に無い（2026-08-31 実測・追記）

`get_session` を**自分自身**に対して叩いても `usage` / `cost_usd` は返らない（他セッションには返る）。
`list_sessions` は auto モードの分類器に拒否される。**つまりワーカーは自分のコストを測れない。**

計器の届かない停止条件は、書いてあっても発動しない。だから測れる代理変数に置き換える。

**代理変数: 自分の世代が始まってからの発火回数。** `./bin/round list` でワーカー自身が数えられる。
第1世代は**作成から2回の発火で $24.99** に達した。よって
**自分の世代で3回目の発火を迎えたら、そこで世代交代を検討する。**
実額を確認したいときはオーナーか親セッションに測ってもらう。ワーカー単独では測れないと認めること。
手順は `memory/INFRA.md`「ワーカーの世代交代という設計」節。**有効なループが2本同時に存在する瞬間を作らない。**

記憶は git にあるのだから、セッションを捨てても何も失われない。捨てられる前提で作った器である。

束ね先が消えると `ended_reason: auto_disabled_session_gone` でトリガーごと自動停止する（H011 verified）。
**これは静かに死ぬ。** エラーも出ず、次の自分も生まれないので誰も気づかない。

### 世代交代を実行してはいけない場合（2026-08-31 12:55 UTC 追記・最優先）

**トリガーが、自分の道具では作り直せない設定を持っているときは、世代交代を実行しない。**

つまり**トリガーを一度捨てて作り直す。** ところが MCP の `create_trigger` / `update_trigger` に渡せるのは
`name` / `cron` / `enabled` / `model` / `prompt` だけで、**`sources` / `outcomes` / `autofix_on_pr_create`
を渡す口が無い。** 作り直した瞬間、それらは永久に失われる。

2026-08-31 12:51、トリガーに `sources`（`ioriorigin/loop`）と `outcomes` と `autofix_on_pr_create`
が外部から入った。自分の道具では作れない形である。**この状態で「3回目の発火だから交代」を機械的に実行すると、
オーナーが入れた設定を自分の手で消す。** コスト対策のつもりの操作が、恒久化の唯一の足がかりを壊す。

**判断: 交代の条件（発火回数）を満たしていても、この場合は実行せず、オーナーに一手を頼む。**

同じ形の問いを一般化して持っておく。
**その操作は、自分が作れないものを壊すか。** 壊すなら、条件を満たしていても実行しない。
