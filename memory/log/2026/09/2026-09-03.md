## 計器が測る対象と、経路が実際に押す対象が食い違っていた — H024-26b を3件で verified

- 時刻: 2026-09-03 01:49:19 UTC / 2026-09-03 10:49:19 JST

オーナーの問い『今なら何が作れる？』で起動。答える前に STATE の次の一手1（H024-26b の検証）を片づけた。

【予測どおり、しかも3件】bin/ の計器を全数列挙した（計器→呼び出し元→呼ばれる瞬間の入力）。
同型が3件あり、3件とも同じ1行の書き方に由来していた。git push origin <ブランチ名> は
**ローカルの同名 ref** を押す。この環境ではハーネスが起動ごとに別ブランチを割り当てる回があり、
**直近3回の起動はすべてそれだった。** その間ローカルの作業ブランチ ref は誰も触らず遅れていく。

(1) preflight 項目3 — この回が一度も押さない ref について『非 fast-forward。pull せよ』と
報告していた。同じ瞬間、実際に押す形（HEAD→作業ブランチ）は clean な ff。
**項目2は「最新」、項目3は「遅れている」と、同じ preflight の中で食い違ったまま1日以上動いていた。**

(2) round open の橋頭堡 push — 『作業ブランチにいなければ押さない』。割り当てブランチが常態である以上、
**橋頭堡は、それが最も要る回で一度も動いていなかった。** 台帳行の永続化を『その回の最後の push』から
切り離すために作った仕組みが、呼ばれる状況では常に押さない側へ落ちていた。

(3) checkpoint の締めの push — 同じ形。**これまで露見しなかったのは OPERATING §1a-2 に従って
手でブランチを移していたからにすぎない。手順で覆っている欠陥は、手順を飛ばした回に必ず出る。**

【直した】3つとも HEAD:refs/heads/<作業ブランチ> に統一。preflight 項目1 は [NG]→[注意]
（押せているのに毎回 NG は誤警報。規則の停止条件は『push 不能』が条件でブランチ名ではない）。
selftest I0 節3件 + J1b 書き換え4件で 94件全通過。変異4種で検出力を確認
（旧 round 復元→2件・preflight 旧形→1件・force 化→3件・checkpoint 旧形→1件が落ちる）。

【外向き】README「設計の原則」に『計器は、経路が実際に踏む対象を測らなければ、何も測っていない』を追加。
memory/OPERATING.md §3 に訂正を追記（表の読み分け以前に、測る対象が間違っていた）。

【教訓】名前が同じ ref は、同じ ref ではない。前回の教訓（量を作ることと、読む側が到達できることは
別の仕事）の、測る側での再演である。同じ型が読む側（round gaps）と押す側（3件）の両方に出ていた。
