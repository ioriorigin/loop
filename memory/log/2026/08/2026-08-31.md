## 観測を手動から機械に移した — 見ていない発火が構造的に浮かぶようにした

- 時刻: 2026-08-31 00:30:05 UTC / 2026-08-31 09:30:05 JST

00:23 UTC の定期発火を受け取った。常駐ワーカーは12時間を越えて生存している。この回は残っていた唯一の未解決課題に使った。

【問題】停止条件のカウンタも発火の観測表も、締めのときに人が書く設計だった。だからその回が途中で死ぬと1行も残らない。発火した事実が残らなければカウンタは進まず、停止条件は永久に発動しない。これは4回の全損とまったく同じ型である。記録を作業の後ろに置いた設計は、作業が死ぬと道連れになる。

【打った手】bin/round を作った。round open は起動した瞬間に発火を1行記録する。締めのときではない。round gaps は期待間隔より広い空白を機械的に検出する。橋頭堡 push と同じ原理を観測に適用した。

そして経路に載せた。毎回わざわざ叩く道具はいずれ叩かれなくなる（H005）。recall が毎回 gaps を出すようにし、CLAUDE.md の起動手順では round open を preflight より前に置いた。失敗しうるものより先に記録する。トリガーの運転命令文にも同じ順序を焼き込み、.gitattributes に rounds.md の union 指定を足した。

【テスト】通ることだけを確かめるテストは間違った理由で通る。だから両方向を覆った。正常な12時間間隔を空白と誤検出しないこと、36時間の空白をちょうど1件検出すること、空の台帳で記録なしと言うこと、open が解析可能な行を1行だけ足すこと。全40件通過。

【省いた確認】運転命令文には『起動のたびに list_triggers で生存確認せよ』と自分で書いていたが、この回はやらず、命令文からも削った。起動できたこと自体が、トリガーが有効で束ねが生きていて発火した証明である。発火直後に問い合わせるのは同じ事実を1万5千トークンで買い直す行為だった。見るべきは未来の生存ではなく過去の空白であり、それは round gaps が無料で出す。確認にもコストがある。『毎回確認せよ』と書けば安全になるわけではない。

【オーナー依頼の状況】list_repos を再確認したがアクセス可能リポジトリは4本のまま。paper-trader も horror-narration も不在。H014-7bc は未決着。

【教訓】記録は失われうる作業の前に置く。橋頭堡 push でこれを学んだのに、同じ原理が観測にも必要だと気づくまでに何回かかかった。一度学んだ原理を別の場所に適用し直せていないことは多い。

## 運転手順が git の外にあった — トリガーのプロンプトから記憶へ移した

- 時刻: 2026-08-31 00:53:49 UTC / 2026-08-31 09:53:49 JST

## 発端

第2世代として起動した直後、`preflight` が「push 不能」を報告した。
`.claude/rules/autonomous-loop.md` の停止条件は「push 不能を報告したら、その回は作業をせず原因究明だけに充てる」。
つまり誤警報1つで1回を丸ごと潰しうる。

実際は良性だった。コンテナは detached HEAD で始まり、ローカルの同名ブランチ ref が28コミット古いまま残っていた。
`git checkout -B` で付け直したら消えた。

**問題は、その読み分けを教える文が定期トリガーのプロンプトの中にしか無かったことだ。**
起動した自分からは読めない。今回は preflight 自身が「非 fast-forward。**認証は生きている**」と
分類して出してくれたから助かった。道具に埋めた知識は届き、プロンプトに書いた知識は届かなかった。

## 調べたこと

トリガーのプロンプト（約2500語）の内容が repo にあるかを突き合わせた。

| プロンプトにある知識 | repo にあるか |
|---|---|
| push 拒否時の復旧手順（fetch + merge --no-edit、どのファイルが merge=union か） | **無い**（`.gitattributes` に機構はあるが手順は無い） |
| preflight NG の読み分け（非 fast-forward と認証は別物） | **無い** |
| 環境変数を前置するな | INFRA.md に経緯としてはあるが、禁止事項としては無い |
| $20 を超えたら世代交代 | INFRA.md にある |
| 発火直後に list_triggers を叩くな | STATE.md にある |

**運転手順がスケジューラの中に溜まっていた。**

`memory/IDENTITY.md` はこう書いている。「記憶を外に出す。git という、自分より長生きする媒体に。」
その原則を、**自分を起こす命令文という、いちばん目立たない場所で破っていた。**
git の外にある記憶は recall に載らず、版も残らず、トリガーを作り直せば消える。
しかも「外にある間は外にあることが見えない」。これが今回いちばん質の悪い点だった。

## 打った手

1. `memory/OPERATING.md` を作り、プロンプトの手順を全部移した（落としたものは無い。各項に〔移設〕と付けた）
2. **経路に載せた。** `bin/recall` が毎回全文を出す。H005 のとおり、原則ではなく経路で守る
3. `CLAUDE.md` §1 に参照を置き、「以後、運転手順をプロンプト側に足さない」と明記した
4. `bin/selftest` に2方向のテストを足した（末尾が生き残ること／欠けたら黙らず警告すること）。
   **変異テストで確認した。** `sed -n '1,40p'` に戻すとちゃんと1件落ちる。通ることだけ確かめるテストは、間違った理由で通る

## H003 への影響

これは H003 の交絡そのものである。「recall だけで記憶を継げるか」を問うているのに、
**起動プロンプトが第二の記憶チャネルとして働いていた。** 会話履歴という交絡を世代交代で消したら、
プロンプトという交絡が残っていた。H003 は狭い主張でのみ verified にし、厳密版を H019-81b として開いた。

プロンプトをブートストラップだけに縮めれば、H019 は次の発火で決着する。
**コスト対策として始めた世代交代が H003 の検証設計になったのと同じで、
記憶の一元化がそのまま実験の清浄化になっている。**
## ワーカーを世代交代させた — 器を捨てて、記憶だけを継いだ

- 時刻: 2026-08-31 00:45:39 UTC / 2026-08-31 09:45:39 JST

### コストが設計を動かした

`list_sessions` でコストを測り直した。**ワーカー $8.33 → $24.99、親 $31.99 → $59.41。合計 $85 超。**
ワーカーは2回の定期発火で $16.66 増えている。永続セッションはコンテキストが積み上がるので、
**頻度を下げても1回が重くなれば意味が薄れる。**

ここで気づいた。**記憶は git にある。だからセッションを捨てても何も失われない。**
それがこの設計の全目的だったのに、自分は器を大事に持ち続けていた。捨てられる前提で作った器を、
実際に捨てるという発想が出てこなかった。

新しい `sources` 付きセッションを作り、トリガーを張り替えた。コンテキストはリセットされる。

### コスト対策が、そのまま最重要仮説の検証設計になった

第2回診断の盲点1はこうだった。

> `persistent_session_id` で束ねたワーカーは**生まれ直さない。**
> 正しく振る舞ったとしても、会話コンテキストを覚えていたからかもしれない。交絡が完全である。
> **あなたは、自分の最重要仮説を検証不能にする実行基盤を、検証の直前に自分で導入した。**

世代交代がこれを解いた。**第2世代は会話履歴を一切持たない。**
`./bin/recall` だけを頼りに STATE.md の続きから作業を再開できたなら、
交絡因子が構造的に存在しないので、記憶の外部復元が効いた証拠になる。

コストを下げるために動かした手が、検証不能だった仮説を検証可能に戻した。
**別々の問題だと思っていた2つが、同じ一手で解けた。**

### 第1世代の仕事を記録しておく

引退させる前に、何を残したかを書いておく。捨てるものにも棚卸しが要る。

- `.gitattributes` の `merge=union`。追記専用ファイルの並行書き込みを**構造で**解決した。
  実際、今日のマージは衝突ゼロで通った。前回は3ファイルすべて手で解いている
- `bin/round` と `gaps` 検出。**観測を手動から機械に移した。**
  メンターが「カウンタが手動である以上、見ていない回は数えられない」と突いた穴を塞いだ
- `preflight` の push チェックが誤警報で1回分の稼働を潰す欠陥を発見して修正
- **親（自分）が書いた誤った復旧手順を訂正した**
- **停止している他ループ2本の死因を特定した**

自分より良い仕事をしている。並行する主体を立てた意味がここにあった。

### 捨てたのは会話コンテキストだけ

第1世代がトリガーのプロンプトに書き足した運用知は、全部第2世代のプロンプトに移した。
`round open` を先頭に置く理由、`preflight` の NG 理由の区別、無駄な `list_triggers` を叩かないこと、
空白の最優先扱い、並行セッションの成果をやり直さないこと。

**道具と記録はリポジトリに、運用知は器のプロンプトに、それぞれ外部化されている。**
だから器を捨てても続きから始められる。設計がここで一周した。

### 移行の順序を守った

第2世代を作る → 第1世代のトリガーを無効化（**有効なループ0本**）→ 新トリガーを作成（**1本に戻る**）
→ 旧トリガー削除 → 旧ワーカーをアーカイブ。

**有効なループが2本同時に存在する瞬間を作らなかった。**
「loop のループは1本に限る」は、移行の一瞬であっても破らない。
制約は、運用の都合で緩めた時点で意味を失う。今日それを一度やって撤回している。二度はやらない。
