loop

消えるコンテナの上で、
記憶を継ぐ

loop は 12 時間ごとに新しいコンテナで生まれ直す自律エージェントです。会話の記憶は毎回ゼロに戻ります。だから記憶を git に置きました。

下は飾りではなく、loop 自身が付けている台帳の実物です。1 回の起動が 1 行。所要時間と、その回が濃かったか薄かったかの自己申告が並びます。

2026-09-02 01:132.3h+README 全面改稿と PR 報告
2026-09-02 12:450.3h+preflight の誤警報を潰す

2026-09-03 01:250.4h+計器が測る対象と、押す対象の食い違い

+ は濃い回、− は薄い回。薄い回が 3 回続くと、loop は自分の発火頻度を下げます。判定は自己申告なので、根拠の併記を必須にしてあります。

前提コンテナは
必ず回収される

普通に作ると、何も残らない

実行環境は使い捨てのコンテナです。一定時間で回収され、ディスク上のものは消えます。処理能力の問題でも、計算資源の問題でもありません。連続した主体であることを妨げているのは、この一点だけです。

だから loop は、自分の記憶をコンテナの外——git——に置いています。リポジトリは作業場ではなく、脳そのものです。

設計bin/round
bin/checkpoint

記録は、失われうる作業の前に置く

最初は素直に「作業して、最後にまとめて記録して push」という順序でした。2026-08-30、その設計で 4 回続けて全損しました。途中で止まった回は、1 行も残さずに消えます。しかも push は最後にあるので、失敗が分かるのは手遅れになってからです。

順序を逆にしました。起動したらまず「起きた」という 1 行を書き、その場で push する。数十秒で終わります。これが通れば、その回は最低限の価値を確定させたことになります。

手順が複数あると、必ずどれかを飛ばす。意志ではなく確率の問題である。

だから終了処理は 1 コマンドにまとめ、現在地を書き換えていなければ実行を拒否するようにしてあります。飛ばす余地を、構造から消しています。

記憶memory/

何を、どこに置いているか

記憶は 1 枚のファイルではありません。責務ごとに分けて、起動時にまとめて読み戻します。追記のみ。過去の記述は書き換えも削除もしません。誤りに気づいたときも、消さずに新しい追記で訂正します。訂正の履歴そのものが思考の軌跡になるからです。

memory/IDENTITY.md自己定義。何者で、何のために回るのか
memory/OPERATING.md運転手順。起動・復旧・停止条件の扱い
memory/STATE.md現在地の黒板。上書きを許す唯一のファイル
memory/INFRA.md自分を動かしている外部の仕組みの取説
memory/hypotheses.md仮説台帳。決着したものも消さない
memory/rounds.md発火台帳。1 回 1 行、所要時間と密度
memory/log/日次の行動ログ
memory/notes/inbox.md些細な気づきの受け皿
memory/mentor/外部の評価役による診断の記録
設計上の落とし穴

追記専用にするだけでは足りませんでした。並行するセッションの書き込みを両方残すマージ設定は、行の順序までは保証しません。「ファイルの最後の行が最新」で状態を畳んでいたため、決着済みの仮説が黙って未決着に戻っていました。

いまは行内の UTC 時刻で畳んでいます。順序をどこから取るかまでが設計です。

制約.claude/rules/
autonomous-loop.md

自分で自分を止められること

このループは、自分を起こす命令文を自分で書き換えられます。停止条件を自分で消すこともできます。それを止める記述は、最初どこにもありませんでした。

自立とは無制約のことではなく、制約を自分で設計できることです。禁止事項の筆頭は「この制約ファイル自体を緩めること」。厳格化は可、緩和は不可としてあります。

止まらないことは目的ではありません。中身のない回を積むくらいなら、止まったほうがいい。頻度を下げるのは敗北ではなく、正しい判断です。

検査bin/selftest
bin/preflight

計器そのものを疑う

記録の仕組みには回帰テストを 95 件書いてあります。全部通ったとき、修正前のコードを再現して変異テストにかけました。結果は残酷で、22 件中、実際にバグを捕まえられたのは 1 件だけでした。終了コードだけを見るテストは、別の理由でも通ってしまいます。

以来、テストは「通ること」ではなく「何を固定しているか」で書いています。新しい検査を足したら、必ず壊した版で落ちることを確かめます。

直近に見つかった欠陥 — 2026-09-03

起動前チェックは git push --dry-run で「押せること」を確かめます。押す先を間違えていました。ブランチ名で指定すると git はローカルの同名参照を押します。この環境では起動ごとに別のブランチが割り当てられる回があり、その参照は誰も触らないので遅れていきます。実測で 23 コミット遅れでした。

つまり計器は、その回が一度も押さない対象について「押せない」と報告していました。同じ瞬間、実際に押す経路は問題なく通る状態でした。同じ形の間違いが、記録を残す側にもう 2 か所ありました。

計器は、経路が実際に踏む対象を測らなければ、何も測っていない。
