## 3. 中身の構成

```
mimetype                     ← **無圧縮で、zip の先頭**（バイト offset 38 に中身が来る）
META-INF/container.xml       ← OPF の場所を指す
OEBPS/content.opf            ← 書誌・manifest・spine
OEBPS/nav.xhtml              ← EPUB3 の目次（**章の下に節がぶら下がる**）
OEBPS/toc.ncx                ← EPUB2 互換の目次（古いリーダー向けに残す）
OEBPS/style.css
OEBPS/cover.xhtml            ← 題扉（画像は持たないのでテキストで組む）
OEBPS/ch00.xhtml … ch07.xhtml
```

### 気をつけた点（仕様上、外すと壊れるもの）

1. **`mimetype` は無圧縮で先頭。** `zipfile.ZIP_STORED` を明示し、最初に書く
2. **`nav.xhtml` に `properties="nav"`。** これが無いと EPUB3 の目次として認識されない
3. **manifest と実ファイルを 1 件も食い違わせない。** 検査で両方向を見ている
   （manifest にあるのに無い／あるのに manifest に無い）

### Markdown 変換で気をつけた点

**コードフェンスの内側を先に切り分けること。** これが最大の落とし穴である。

原稿の bash 例は `# 台帳の末尾から遡り…` のようなコメント行を持つ。
素朴に行頭 `#` を見出しにすると、**コード中のコメントが章見出しになる。**
全章で行頭 `^# ` は 19 件あるが、**実際の章見出しは 9 件しかない。**
同じことが `---`（水平線）と `|`（表）にも起きる。

行内記法も順序が要る。**`` `code` `` を最初に退避しないと、コード内の `**` や `[ ]` を
強調・リンクとして誤って解釈する。**

## 4. 組んで初めて見つかった原稿の欠陥

`03-起動手順.md:273` の段落に、**閉じ忘れの `**` が 1 件**あった。

```
前提——**「押せる」こと——を、作業を始める前に確かめる
```

閉じない `**` は、変換すると本文に `**` がそのまま残る（GitHub の表示でも同じである）。
全 8 章を**段落単位で**走査した結果、**この 1 件だけ**だった。
行単位で数えると 57 件出るが、**56 件は 2 行にまたがる正常な強調である**——
ここを行単位で見ていたら、正常な 56 件に埋もれて 1 件を見落とすか、全部を誤検出していた。

修正し、**症状ではなく原因の名前で落ちる検査**を別に足した（`check_epub.py` の基準 5-0）。
基準 5（字数の一致）でも落ちるが、そちらは「本文が落ちた」としか言わない。
**何が悪いのかを名前で言う検査を、別に置く。**

## 6. 検査の側が 2 回、嘘をついた（記録として残す）

**基準 5（本文が落ちていないこと）の対照は、2 回続けて偽陽性を出した。**

1. **対照が `**` とバッククォートを、コードブロックの中まで剥がしていた。**
   原稿には `memory/log/**/*.md` という glob や、`**今すぐ原因を潰せ。**` を含む
   `preflight` の実出力がコードブロックに入っている。
   **正しく組めていた EPUB を「本文が落ちている」と 5 章ぶん告発した**
2. 直したあと、**コードブロックを末尾へまとめて付けた。**
   字数は完全に一致するのに並びだけが食い違い、今度は 8 章ぶんが不一致になった。
   **対照は、順序も含めて対照でなければならない**

2026-09-06 に類書の抽出が「全 15 冊がレビュー 0 件・★4.2」と答えたのと同じ型である——
**取れた値がもっともらしいと、当て先を検算しない。**

**ただし今回は、判定基準を組む前に台帳へ書いてあった。**
だから結果は「もっともらしい側」ではなく「食い違った側」に出て、**検算せざるを得なかった。**
先に基準を書くことの利得が、初めて実物で出た回である。
