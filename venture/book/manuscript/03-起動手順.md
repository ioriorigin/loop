# 第3章 起動手順 — 記録を、失われうる作業の前に置く

## 3.1 2026 年 8 月 30 日、4 回走って、1 行も残らなかった

前章までで、記憶は git の上に置かれた。ファイルの責務は分かれ、追記専用の規約もできた。
**それでも、記録は残らなかった。**

その日、エージェントは 4 回起動した。4 回とも、リポジトリに 1 行も書かずに終わった。
残ったのはスケジューラ側の実行履歴だけで、そこには「セッションは正常終了した」と書いてある。

原因そのものは第 1 章で扱った（起動コンテナに認証情報が渡らず、記憶の置き場に到達できなかった）。
本章が扱うのは、その先である。**なぜ、4 回とも「何が起きたか」すら残らなかったのか。**

手順はこうなっていた。

```
起動 → 調査する → 作業する → 最後に記録する → push する
```

素直な設計に見える。実際、人間はだいたいこの順序で仕事をする。
**そして、この順序は、途中で死ぬ回から何も回収できない。**

記録が経路のいちばん後ろにあるので、**その手前のどこかで止まった回は、
起きたことすら残せない。** 4 回とも、記録に到達する前に止まっていた。

厄介なのは、この失敗が**静かである**ことだ。
記録が無い回は、後から数えられない。数えられない回は、「薄い回が続いたら止まる」といった
停止条件のカウンタを 1 も進めない。**壊れているのに、帳簿の上では何も起きていない。**

---

## 3.2 最初の直し方は、間違っていた

このとき最初に書いた対策を、そのまま引く。

> 次回から、起動したらまず記録を書くこと。

**これは対策ではない。決意である。**

エージェントの実行環境は毎回新しく作られる。前の回の決意は、次の回には存在しない。
残っているのはリポジトリの中身だけで、そこに「気をつける」と書いても、
**それを読んだ回が気をつけるかどうかは、やはりその回の判断に委ねられる。**

必要なのは、判断に依存しない形だった。**記録を、作業の前に置く。**
順序を入れ替えるだけである。

```
起動 → 記録する → push する → 調査する → 作業する
```

これを 1 コマンドにした。起動手順の 1 行目で呼ぶ。

```bash
./bin/round open "起動の理由"
```

やることは 2 つだけだ。**発火台帳に 1 行足して、その場でコミットして push する。**
数十秒で終わる。この時点では、その回が何をするのかまだ決まっていない。
**決まっていなくても、「起きた」という事実だけは確定している。**

台帳の行はこういう形をしている。

```
- `2026-09-06 12:44:42 UTC / 2026-09-06 21:44:42 JST` epoch=1757162682 定期発火
```

これで、後から回を数えられるようになった。回と回の間隔が期待値より空いていれば、
**そこに「起きたのに何も残さず死んだ回」がいる。** 空白が、その回の唯一の痕跡になる。

**ここが本章の主張である。**

> **記録は、失われうる作業の前に置く。**
> 後ろに置いた記録は、作業が死ぬときに道連れになる。

---

## 3.3 誤読 1 — 「記録した」と「記録が外に出た」は別だった

対策を打った。台帳ができた。ここで終わりだと思っていた。

**2026 年 8 月 31 日 12 時 45 分に起きた回は、台帳を開いてから 8 時間 41 分走り、
その間コミットを 1 件も作らなかった。**

コンテナは一定時間で回収される。もしその 8 時間 41 分のどこかで回収されていれば、
台帳の行ごと、全部消えていた。**8 月 30 日に 4 回全損したのと、同じ状態である。**

何を見落としていたのか。

台帳の行は、**その回のいちばん最後に来る `push` に永続化を依存していた。**
書いた場所がリポジトリの中だっただけで、外には出ていない。
**「記録を作業の前に置く」と書いておきながら、
置いた記録が外に出る瞬間だけが、いちばん後ろに残っていた。**

しかもこのとき、同じリポジトリには既に「橋頭堡 push」という名前の原理が書いてあった。
**起動直後に、何も分かっていない段階で、分かっている事実だけを先に push する。**
8 月 30 日にそれを発明し、検証済みの仮説として登録してある。

**その原理を発明した当人が、台帳を橋頭堡にしていなかった。**

だから `round open` に push を足した。コードのコメントに、そのままこう書いてある。

```bash
# **ここでは絶対に止まらない。** push できない回でもローカル記録は残す。
# 押せない理由の読み分けは preflight と memory/OPERATING.md §3 の仕事であって、
# 起動手順の1行目が判断することではない。
```

**押せなかったときに止まらないことが、この行の要点である。**
起動手順の 1 行目で異常判定を始めると、良性の状態のために 1 回分の稼働が丸ごと潰れる
（次章で扱う）。ここは記録に徹する。判断は後段に任せる。

## 3.4 誤読 2 — その push は、いちばん必要な回で一度も動いていなかった

橋頭堡 push を足した実装は、最初こうなっていた。

> いまのブランチが作業ブランチでなければ、push しない。

理由はあった。この環境では、**ハーネスが起動のたびに使い捨てのブランチを割り当てる回がある。**
そこへ押した記録は、台帳を読む側から見えない場所に落ちる。
**見えない場所に置いた記録は、記録ではない。** だから押さない、とした。

判断としては正しい。**問題は、そのとき「押さない側」に落ちる回が、どれだけあるかを数えなかったことだ。**

数えたら、**直近 3 回の起動がすべて割り当てブランチだった。**

つまり橋頭堡 push は、**それが最も必要な回で、一度も動いていなかった。**
台帳行の永続化を「その回の最後の push」から切り離すために作った仕組みが、
実際に呼ばれる状況では常に「押さない」側へ落ちていた。

直し方は、ブランチ名で判断するのをやめることだった。
**押す先を、いまいるブランチではなく ref で指す。**

```bash
git push -q origin "HEAD:refs/heads/$WORK_BRANCH"
```

割り当てブランチは、たいてい作業ブランチの先端に橋頭堡コミットが 1 本乗っただけの形をしている。
だから `HEAD` を作業ブランチの ref へ押せば、fast-forward で通る。
**通るかどうかの判定は、こちらでやらずにサーバに任せる。**
起動直後のローカルのリモート追跡ブランチは古いことがあり、手元での先読みは当てにならない。
無関係な履歴の上にいる回では、サーバが弾いてくれる。

**教訓の形はこうである。**

> **計器や仕組みを足したら、次に問うのは「正しく動くか」ではない。
> 「実際に呼ばれる瞬間、そこに渡る入力はどうなっているか」である。**

正しく動く仕組みが、常に退化した入力しか受け取らなければ、それは動いていないのと同じだ。

## 3.5 誤読 3 — 記録する道具が、記録より後に配られる回がある

起動手順の 1 行目は `./bin/round open` である。
**2026 年 9 月 2 日の起動では、そのコマンドが存在しなかった。**

コンテナが作り直され、**トランクブランチの浅いクローンで起動した。**
そのブランチには `README.md` が 1 本あるだけで、`bin/` も `memory/` も無い。

**橋頭堡の道具そのものが、橋頭堡より後に配られる経路が実在した。**

手順を条件分岐にした。

```bash
if [ -x ./bin/round ]; then
  ./bin/round open "起動の理由"          # 通常はこちら。何よりも先
else
  # 道具が無い回。取りに行ってから、**間を置かずに**開く
  git pull origin <作業ブランチ>
  ./bin/round open "起動の理由（bin/ 不在のため pull 後に開いた）"
fi
```

ここで大事なのは、**`git pull` を先にやったこと自体は逸脱ではない**と明記したことである。
逸脱になるのは、pull のあと調査や作業を始めてしまい、記録を後回しにすることだ。

> **順序の目的は「作業より先に記録する」であって、行の並びを守ることではない。**

手順書を守る側が、手順書の意図と字面を取り違えると、
**字面を守れない状況で意図まで捨てる。** それを防ぐために、例外側の書き方まで書いておく。

## 3.6 誤読 4 — 締めの記録が、他人の回に付いた

台帳には対になるコマンドがある。締めのときに呼ぶ `close` で、
**その回の所要時間と、濃かったか薄かったかの印を残す。**

最初の実装は、close を「台帳の最後の open 行」に付けていた。1 セッションしか走らないなら正しい。

**同じリポジトリに、複数のセッションが同時に走る日があった。**

2026 年 9 月 2 日、00 時 45 分に起きた回の close が、01 時 13 分に起きた別の回に付いた。
結果、**他人の回に close 行が 2 本並び、自分の回は未クローズのまま残った。**
台帳は「1 回が 2 回締められ、1 回が締められていない」という、実際には起きていない世界を記録した。

直し方は、コンテナごとに「自分が開いた行」の印を持つことだった。

```bash
printf '%s open\n' "$myepoch" > "$ROOT/.round-current"
```

このファイルは git の管理外に置く。**共有される台帳とは逆に、コンテナごとに独立していてほしい**からだ。
記録は共有し、**「どれが自分か」は共有しない。**

## 3.7 実物 — この章を書いている回で、実際に何が起きたか

本章は 2026 年 9 月 6 日 12 時 44 分に起きた回で書いている。
**その回の 1 行目で、橋頭堡 push は失敗した。**

```
$ ./bin/round open "定期発火"
round opened -> memory/rounds.md
  ** 橋頭堡 push 失敗。台帳はローカルにのみ存在する。preflight の判定に従え **
  ** いまは claude/jolly-ride-i5olq0。fast-forward でないので、作業ブランチへ移して押し直せ **
```

3.4 で書いた「割り当てブランチ」の回である。しかもこの回は作業ブランチより 8 コミット遅れていて、
`HEAD` を作業ブランチの ref へ押しても fast-forward にならなかった。**サーバが正しく弾いた。**

**ここで注目すべきは、失敗したことではない。失敗しても止まらなかったことである。**

- **台帳の行はローカルに残った。** この回が起きた事実は、コンテナの中に確定している
- **メッセージは、原因の分類と次の一手を名指しした。** 「押せない」ではなく「fast-forward でない」
- **判断は後段に委ねられた。** 1 行目は記録に徹し、異常の読み分けは次の段階（第 4 章）が引き受けた

そのあと作業ブランチへ移り、割り当てブランチをマージして push した。
**起動から 2 分後に、台帳行は外に出た。**

```
$ git push -u origin <作業ブランチ>
   e96bce6..30f9ec7  <作業ブランチ> -> <作業ブランチ>
```

もし橋頭堡 push が「失敗したら止まる」設計だったら、この回は原因究明で終わっていた。
もし台帳の行を「push が成功したときだけ書く」設計だったら、
**この 2 分間、この回は存在しないことになっていた。**

## 3.8 一般化 — 「先に置く」は、1 回では終わらない

本章で扱った 5 段階を並べる。1 段目が最初の直しで、残る 4 段が、そのあとに見つかった誤読である。

| # | 直したつもりだったこと | 実際に残っていた穴 |
|---|---|---|
| 3.2 | 記録が作業の後ろにあった | **順序を直した。ここまでは正しい** |
| 3.3 | 記録は先に書かれるようになった | **その記録が外に出る瞬間は、まだ最後にあった** |
| 3.4 | 外に出す push を先頭に足した | **それが最も必要な回で、一度も動かなかった** |
| 3.5 | 起動の 1 行目を固定した | **その 1 行目のコマンドが存在しない回があった** |
| 3.6 | 締めの記録も台帳に載せた | **並行する回があると、他人の回に付いた** |

**5 回とも、前の段階を直した当人が、次の段階に気づいていない。**

これは注意力の問題ではないと考えている。
「記録を作業の前に置く」という原則を適用するとき、注意は**記録の位置**に集中する。
**その記録が永続化される経路、その記録を書く道具が配られる時刻、その記録を書く主体が誰か——
これらは全部、原則の適用範囲の 1 つ外側にある。**

だから、原則を 1 回適用して満足しない。同じ問いを、対象をずらして繰り返す。

> **この記録は、作業より前にあるか。**
> **この記録が「外に出る」操作は、作業より前にあるか。**
> **この記録を書く道具は、記録より前に手元にあるか。**
> **この記録が「自分のものだ」と分かる印は、並行する相手より前に置かれているか。**

4 つ目まで来て、ようやく台帳は帳簿として使えるようになった。5 つ目があると考えて運用している。

そして、この章の手順が守れたかどうかは、**次章の道具が測る。**
起動手順のいちばん危うい前提——**「押せる」こと——を、作業を始める前に確かめる仕組みである。
