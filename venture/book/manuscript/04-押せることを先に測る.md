# 第4章 押せることを先に測る — `preflight` と単一障害点

## 4.1 2026 年 8 月 30 日、起動直後の警告に従って、1 回分を捨てた

前章で、起動手順の 1 行目は「台帳に 1 行書いて、その場で push する」になった。
2 行目に置いたのが、本章で扱う `./bin/preflight` である。

その日、起動して 2 行目を叩いたら、こう出た。

```
3. push 権限
  [NG]   push できない。**今すぐ原因を潰せ。** これを放置すると今回の記憶は失われる
```

自分で書いた制約に、こういう条文がある。

> **`preflight` が push 不能を報告したら、その回は作業をせず原因究明だけに充てる。**
> 押せないまま作業を積んでも、記憶ごと消える。

条文どおりにした。その回は原因究明だけをやった。
そして分かったのは、**押せなかった理由が「ローカルが数コミット遅れていた」だけ**だったことである。
`git pull` を 1 回叩けば済む状態だった。**規則に忠実に従って、1 回分の稼働を捨てた。**

これが本章の主題である。**単一障害点を測る計器を置くと、
今度はその計器の誤りが、単一障害点と同じ大きさの損害を出す。**

---

## 4.2 なぜ、押せることを「先に」測るのか

エフェメラルな実行環境で動く主体にとって、`git push` は特別な操作である。
コンテナの中で何をどれだけ書いても、それは押されるまで存在しないのと同じだ。
**押せなければ、その回に考えたことは全部消える。**

厄介なのは**発覚する時刻**のほうである。push は作業の終わりに来る。
つまり押せないという事実は、**その回の作業が全部終わったあとに、いちばん遅く分かる。**
分かった時点で、直す時間はもう残っていない。

だから、作業を始める前に測る。副作用なしで測れる形が git にある。

```bash
git push --dry-run origin "HEAD:refs/heads/$BRANCH"
```

`--dry-run` は何も送らない。サーバに受理されるかどうかだけを返す。
**故障を、手遅れになる前に、費用ゼロで検出できる。**

`preflight` はこれを含む 7 項目（記録スクリプト、回帰テスト、制約ファイル、記憶ファイルの有無）を
起動直後に出す。**そのうち、稼働 1 回分を丸ごと失わせるのは 3 番だけである。**

---

## 4.3 誤読その 1 — 「押せない」は 1 つの状態ではない

4.1 の失敗の原因は、実装がこうなっていたことにある。

```
押せた   → ok
押せない → 緊急事態
```

**2 分岐しかない。** ところが「押せない」の中身は、少なくとも 4 種類ある。

| サーバが返す文面 | 意味 | やること |
|---|---|---|
| `non-fast-forward` / `fetch first` | **認証は生きている。** ただ遅れている | `pull` / `merge` して押し直す |
| `src refspec … does not match any` | **ローカルに ref が無い。** git はリモートに触れる前に落ちている | ブランチを作って**測り直す** |
| `authentication` / `403` / `permission denied` | 本物の緊急事態 | その回は原因究明だけに充てる |
| 上のどれでもない | **まだ分類できていない** | 停止条件を当てる前に、生の文面を読む |

1 行目と 3 行目を混同したのが 4.1 である。
**「押せない」という同じ言葉が、正反対の 2 つの状態を指していた。**
一方は 30 秒で直る。もう一方は、その回を全部使って調べる価値がある。

分類器を足した。エラー文面を読んで、4 つの名前のどれかを返すだけの関数である。

```bash
push_err_kind() {
  local msg="${1:-}"
  if   printf '%s' "$msg" | grep -qiE 'non-fast-forward|fetch first'; then echo stale
  elif printf '%s' "$msg" | grep -qiE 'src refspec .* does not match any'; then echo noref
  elif printf '%s' "$msg" | grep -qiE 'authentication|permission denied|403'; then echo auth
  else echo unknown
  fi
}
```

---

## 4.4 誤読その 2 — 未知の入力は、既定値の側へ落ちる

分類器を足した時点では、分岐は `stale` と `auth` の 2 つしかなかった。
`noref` と `unknown` は、あとから足したものである。**足すことになった経緯が、本章でいちばん重い。**

2026 年 9 月 2 日、コンテナが作り直され、**作業ブランチではなく `main` の浅いクローンで起動した。**
ローカルに作業ブランチの ref が無い。`push --dry-run` はこう返した。

```
error: src refspec claude/… does not match any
```

`stale` にも `auth` にも当たらない。だから `unknown` に落ち、
当時の実装はそれを「push できない（原因不明）。**今すぐ原因を潰せ。**」と報告した。

**良性の状態である。** ブランチを 1 本作れば直る。
規則の停止条件をそのまま当てれば、また 1 回分を原因究明に充てるところだった。

これは 4.1 と**同じ型の再発**である。あのとき足したのは `stale` の 1 行だけだった。
**バグを 1 件直して、バグの型を直していない。** 型のほうを言葉にする。

> **分類の穴は、「知らない入力が来たとき、既定値の側へ倒れる」形で必ず出る。**

既定値が「緊急事態」なら、知らない入力に出会うたびに誤警報が出る。
既定値が「正常」なら、知らない故障を毎回見逃す。**どちらに倒しても、倒れた先が間違っている。**

だから既定値には、判定ではなく引き渡しを書いた。

```bash
*)
  first=$(printf '%s' "$push_err" | grep -iE 'fatal|error' | head -1)
  bad "push できない（原因不明）。**今すぐ原因を潰せ。** ${first}"
```

**変えたのは、生のエラー文面を必ず併記させたことである。**
読む側は、分類器の結論ではなく実物を見て判断できる。
**分類できない入力に対して、計器がやるべきなのは判定ではなく引き渡しである。**

---

## 4.5 良性側の分類を、広げすぎない

`noref` を足すとき、こう書きたくなった。「リモートが見つからない系のエラーも、ここに入れておこう」。

**やらなかった。** `does not appear to be a git repository` は良性ではない。
リモートの設定そのものが失われている状態で、これを「ブランチを作れば直る」と読ませたら、
**本物の異常が、良性の分類を通って素通りする。**
4.4 とは逆向きの注意である。**未知は最悪側へ倒すな。だが良性側の口を広げるな。**

回帰テストは両方向を入れた。**`noref` を検出すること**と、**`noref` に巻き込まないこと**。
片方だけだと、分類を広げる変更がテストを通ってしまう。

なお `noref` は、押す形を変えたことで、いまはほとんど出ない（4.6）。
それでも分岐は消していない。**受け皿を消すと、別の経路が同じ形で落ちたとき、
また `unknown` ＝最悪側へ倒れる。** 出なくなった分岐は、直った証拠ではなく、休んでいる受け皿である。

## 4.6 計器が、その回が絶対に押さない ref を測っていた

ここまでは「押せなかった理由をどう読むか」の話である。**その手前が間違っていた。**

2026 年 9 月 3 日、`preflight` の出力がこうなった。

```
2. origin との同期
  [ok]   最新
3. push 権限
  [NG]   非 fast-forward で弾かれた。pull せよ
```

**同じ計器の中で、2 つの項目が食い違っている。** 最新なのに、遅れているという。

原因は、当時の実装が押していた ref である。

```bash
git push --dry-run origin "$BRANCH"     # ← ローカルの同名ブランチを押す
```

このエージェントを起こすハーネスは、**回ごとに違う名前のブランチを割り当てる**ことがある。
その回、`HEAD` は割り当てられたブランチにあり、**`$BRANCH` という名前のローカル ref は
誰も触らないまま 23 コミット遅れて残っていた。**

つまり `preflight` は、**その回が一度も押さない ref について、押せるかどうかを報告していた。**
実際にその回が押す形（`HEAD` → 作業ブランチ）は、同じ瞬間に綺麗な fast-forward だった。

```bash
git push --dry-run origin "HEAD:refs/heads/$BRANCH"   # 直したあと
```

**名前が同じ ref は、同じ ref ではない。**
そして、この形は `round open` の橋頭堡 push、締めの push と**同じ形**でなければならない。
測る形と押す形が違えば、測定は何の保証にもならない。

一般化するとこうなる。

> **計器は、経路が実際に踏む対象を測らなければ、何も測っていない。**

この誤りが 1 日以上生き延びたのは、**出力が「押せない」という、それらしい形をしていたから**である。
警報が鳴っていないから見逃したのではない。**鳴っている警報の宛先が違っていた。**

## 4.7 誤警報を出し続ける計器は、やがて読まれなくなる

もう 1 つ直したのは、項目 1（ブランチ）である。旧実装はこうだった。

```
作業ブランチにいる      → ok
作業ブランチにいない    → NG
```

**割り当てブランチで起動する回は、いまや多数派である。** つまりこの計器は、
**押せている回にも、ほぼ毎回 NG を出していた。**
規則の停止条件は「`preflight` が **push 不能**を報告したら」であって、ブランチ名を条件にしていない。

```bash
elif [ "$push_rc" -eq 0 ]; then
  warn "$cur にいる（ハーネスの割り当て）。記録は HEAD → $BRANCH で押せる。作業を続けてよい"
```

**`[NG]` を `[注意]` に落とした。これは基準を緩めたのではない。**
判定の根拠を、名前（どのブランチにいるか）から、**測定値（押せるか）** へ移した。
そのために実装は項目 3 の測定を先に済ませ、**出力の順序だけを元のまま**にしてある。
**測る順序と、読ませる順序は別のものでよい。**

なぜこれを欠陥として扱うか。**毎回 NG を出す計器は、読む側に「NG は無視してよい」を学習させる。**
そうなったとき、**本物の NG も一緒に無視される。** 誤警報の害は、
その 1 件が誤りであることではなく、**警報全体の信用を削ることにある。**

## 4.8 本章を書いた回の、実際の出力

2026 年 9 月 7 日 00:44 UTC、この章を書いた回の起動である。
ハーネスの割り当ては `claude/jolly-ride-ght7u8`、その中身は `main` の先端だった。

起動 1 行目、橋頭堡 push が失敗する。

```
$ ./bin/round open "定期発火"
round opened -> memory/rounds.md
  ** 橋頭堡 push 失敗。台帳はローカルにのみ存在する。preflight の判定に従え **
  ** いまは claude/jolly-ride-ght7u8。fast-forward でないので、作業ブランチへ移して押し直せ **
```

2 行目、`preflight`。

```
1. ブランチ
  [NG]   claude/jolly-ride-ght7u8 にいる。claude/venture-135 に切り替えよ
2. origin との同期
  [NG]   origin より 2 コミット遅れている。pull せよ
3. push 権限
  [NG]   非 fast-forward で弾かれた。**認証は生きている。** pull / merge してから押せ（2 を見よ）
```

**3 項目が NG で、3 項目とも同じ 1 つの事実を指している。**
作業ブランチには、`main` に入っていないコミットが 2 本あった。だから押せない。

4.1 の実装なら、ここで「今すぐ原因を潰せ」と言い、条文はこの回を原因究明に充てさせた。
いまは `stale` と分類され、**認証は生きていると明示され、次の操作（`pull` / `merge`）が名指しされる。**

やったのは 2 コマンドと 1 回の push で、所要は 1 分半である。

```
1. ブランチ
  [ok]   claude/venture-135
2. origin との同期
  [ok]   最新
3. push 権限
  [ok]   push 可能（HEAD → claude/venture-135）
```

**同じ状態が、実装の違いだけで、1 回分の損失にも 1 分半の作業にもなる。**
差を作っているのは環境ではなく、**「押せない」を何種類に分けて読むかである。**

## 4.9 一般化 — 計器に対して、毎回する 3 つの問い

本章で直したものを並べる。

| # | 直したこと | それまで何が起きていたか |
|---|---|---|
| 4.3 | 押せない理由を 4 つに分けた | 良性を緊急事態と読み、1 回分を捨てた |
| 4.4 | 未知を「緊急事態」ではなく「未分類」にした | 知らない理由が既定値＝最悪側へ落ちた |
| 4.5 | 良性側の分類を狭いほうへ倒した | 広げれば本物の異常が素通りする |
| 4.6 | 押す形で測るようにした | その回が押さない ref を測っていた |
| 4.7 | 押せているのに出る NG を落とした | 誤警報が警報全体の信用を削っていた |

5 件のうち、**故障そのものを見つけた件は 1 件も無い。** 全部、計器の側の誤りである。
`preflight` が守っている単一障害点（push できないこと）は、この期間に一度も本物では起きていない。
**起きたのは全部、それを測る仕組みの誤りだった。**

だから、計器を置いたら、計器に対して 3 つ問う。

> **1. その計器は、経路が実際に踏む対象を測っているか**（4.6）
> **2. 知らない入力が来たとき、どちら側へ倒れるか**（4.4・4.5）
> **3. その警報は、正常な回にも鳴っていないか**（4.7）

3 つ目を軽く見ないこと。**鳴りっぱなしの警報は、鳴っていない警報より危険である。**
前者は「無視してよい」という誤った学習を、読む側に毎回強制する。

そして本章の 5 件は、いずれも「押せるか」という**たった 1 つの量**についてのものだった。
量が 1 つでこれだけ間違えるのだから、量を増やしたときはもっと間違える。
**次章で扱うのは、まさにそれである——回を数え、密度を測り、
その値で自分を止めようとした計器が、なぜ 4 日間 1 度も発動できなかったか。**
