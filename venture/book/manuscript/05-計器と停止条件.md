# 第5章 計器と停止条件 — 測れない条件は発動しない

## 5.1 なぜ、自律エージェントに停止条件が要るのか

前章までで、エージェントは「消えても続く」ようになった。記憶は git にあり、
起動手順は経路に載り、押せるかどうかは作業の前に測られる。

ここで、設計上いちばん厄介な事実が姿を現す。

**このエージェントは、自分を起こす仕組みを自分で書き換えられる。**

本書が題材にしているリポジトリでは、エージェントが自分の起動スケジュールを変更する道具を
持っていた。頻度を上げることも、下げることも、ループそのものを消すこともできた。
そして規則ファイルもリポジトリの中にあるので、**自分を縛る条文を自分で編集できた。**

つまり、外側に壁が無い。スケジューラも規則ファイルも、縛られる当人の手の届く場所にある。

この構造では、「暴走しないように気をつける」は設計ではない。
**自分に課した制約は、自分が外せる。** だから制約そのものより、
**制約が発動するかどうかを決める計器のほうが重要になる。**

本章の主張は 1 行に畳める。

> **停止条件は、参照する量が先に存在しなければ、書いてあっても一度も発動しない。**

そして本章の価値は、この主張が正しいことの証明にはない。
**この主張を自分で書いた当人が、その原則を自分に適用し損ねた記録が 3 段階ぶんある**ことにある。
以下はその 3 段階である。

---

## 5.2 第1段階 — 条文はあった。参照する量が無かった

題材のリポジトリには、初期から次の停止条件が書かれていた。

> **薄い回が 3 回連続したら、頻度を下げるか一時停止する。**

自律エージェントの停止条件として、悪くない文である。
「動き続けること」を目的にすると、中身の無い回を積むだけの機械になる。それを防ぐ条文だ。

**この条文は、書かれてから 3 日以上、一度も発動しなかった。**
理由は単純である。

**「薄い回」の定義が、どこにも無かった。**

薄いかどうかを判定する量が存在しない。だから毎回、締めのときに
「今回は薄かっただろうか」と自問し、そのつど気分で答え、どこにも記録しない。
連続数を数える対象そのものが無い。

外部レビュー（本書の題材では「メンター」と呼ぶ診断役を常駐させていた）に、こう突かれた。

> 参照する量が存在しないまま、停止条件だけが書かれている。

反論できなかった。**自分で「測れない停止条件は発動しない」と何度も書いておきながら、
いちばん自分に不利な条文にだけ、その原則を適用していなかった。**

そこで定義を置いた。**次の 3 つが全部ゼロの回を「薄い回」とする。**

1. 外向きの成果物（リポジトリの外から読める変更・報告）
2. 決着した仮説（検証か反証まで到達したもの）
3. 修正した欠陥（実際に間違っていた箇所の訂正）

ここで 1 つ、意図的な除外がある。

> **自分の道具を新しく作ることは、上のどれにも数えない。**

数えると「やることがないので何か作る」が薄さ判定を素通りしてしまう。
それは本書の題材となった規則ファイルが「最も避けるべき振る舞い」と呼んだものである。
**判定基準は、自分がいちばんやりたくなる逃げ道を塞ぐ形で書く。**

そして判定を機械が読める場所に落とした。台帳に 1 文字で残す。
**濃い回は `+`、薄い回は `-`。根拠の併記を必須にする。**
自己申告なので必ず甘くなる。だから **根拠を書かずに濃いと自称した回は、薄い回として数える。**

これで参照する量ができた。条文はようやく、量を持った。

## 5.3 第2段階 — 量はできた。読む経路が、末尾で必ず躓いた

翌日、実測した。**停止条件は、やはり一度も発動しなかった。**

台帳を読んで連続数を数えるのは `gaps` という副命令である。実装はこうなっていた。

```bash
# 台帳の末尾から遡り、薄い回（-）が続く数を数える
for (i = n; i >= 1 && i > n - 3; i--) {
  if (M[i] == "-") thin++
  else break
}
if (thin >= 3) { print "薄い回が3回連続している" }
```

一見、正しい。実際に薄い回を 3 回続けた合成台帳を食わせれば、ちゃんと警告が出る。

**問題は、この関数を誰がいつ呼ぶかだった。**

`gaps` を呼ぶのは記憶を読み戻す `recall` だけで、`recall` は起動直後に走る。
そして起動直後には、**その回の「起動した」という行がもう台帳に書かれている**
（第 3 章の橋頭堡である。記録を作業の前に置いた結果、こうなる）。

つまり、**台帳の末尾は必ず「いま走っている回」であり、それはまだ閉じられていない。**
印は `-` でも `+` でもなく `?` である。

```
台帳の末尾
  ...
  2026-09-04 00:44   0.2h   +    ← 前の回
  2026-09-04 12:44     ?    ?    ← いま走っている回（必ずここが末尾）
                       ↑
              遡りはここで必ず break する
```

**遡りは、初回で必ず切れていた。** 薄い回が何回続こうと、`thin` は 0 のままである。

これは本章でいちばん重要な観測である。言い直す。

> **参照する量を作ることと、読む側がそこへ到達できることは、別の仕事である。**

「測れない停止条件は発動しない」を一段深く言い直すと、こうなる。
**量があっても、読む経路が必ず躓く形をしていれば、やはり発動しない。**

そして、この欠陥は**普通のテストでは見つからない。**
`gaps` に薄い回 3 連続の台帳を食わせるテストは通る。関数は正しく動いている。
壊れていたのは関数ではなく、**関数が呼ばれる文脈**だった。

だから、こう固定した。

```bash
# 検出器。ここが落ちなければ、この節は何も守っていない
ledger; row 1 -; row 2 -; row 3 -; row 4 open      # ← 末尾に「走行中の回」を置く
out=$("$T/bin/round" gaps 12 2>&1)
grep -q '薄い回が 3 回連続' <<<"$out"
check $? "薄い回3連続は、いま走っている回が末尾にあっても停止条件を出す"
```

**テストの台帳の末尾に `row 4 open` を置いているのが要点である。**
実際の呼ばれ方を再現しないテストは、実際の欠陥を捕まえない。

> **計器を足したときは、その計器を実際に読む経路で、
> 発動する側と発動しない側の両方を試す。**

## 5.4 第3段階 — 自己申告の台帳は、申告しなかった回を原理的に見られない

同じ日、もう 1 段外側に、同じ型の穴が残っていることが分かった。

台帳には別の役目もある。**起動を取りこぼしていないか**を見る役目である。
12 時間ごとに起きる設計なら、行と行の間隔が 12 時間から大きく開いていれば、
そこに「起きたのに何も残さず死んだ回」がいる。それを空白として検出する。

ある日の実測。**06:28 と 09:57 にコミットを残した回が 2 つあるのに、
台帳にはその 2 回の起動行が 1 行も無かった。**
それでも計器は、こう答えた。

```
  記録された発火 17 件。見落とした発火は無い（期待間隔 12 時間）
```

なぜか。直前の行が 04:07、次の行が 12:44 で、間隔は 8.6 時間しかない。
**期待間隔 12 時間の空白に届かない。**

つまり、**間隔の内側で走った回は、間隔を見る計器には原理的に映らない。**

さらに根本的な問題がある。**台帳は自己申告である。**
申告しなかった回は、自己申告の計器からは永久に見えない。
これは実装の欠陥ではなく、**帳簿が 1 冊しかないことの構造的な帰結**である。

解は、会計と同じである。**別の帳簿を突き合わせる。**

**コミットは、その回が走った動かぬ物証である。** エージェント自身の申告ではない。
だから台帳の窓（`open` から `close` ＋余裕まで）と、git のコミット時刻を突き合わせる。
どの窓にも入らないコミットがあれば、そこに台帳を書かなかった回がいた。

```
台帳の窓:   [====回A====]              [==回C==]
コミット:    ● ●    ●        ●   ●        ●  ●
                            ↑   ↑
                    どの窓にも入らない ＝ 台帳を書かずに走った回
```

実際の出力はこうなる。

```
  ** 台帳に1行も書かずに走った回がある。commit 3 件が台帳の窓の外にある **
  (直近 7 日を見た。開いていない回は gaps の空白には出ない)
    8ff5d8b オーナーと名義の回答を憲章に反映し、依頼を A-00
    d4b5953 訂正: 禁止事項5は自分で課した制約であって、オ
    11b15d1 LP を作って公開し、ソースと URL を記憶に入れた
```

**一般化する。**

> **自己申告の計器は、申告しなかったケースを検出できない。
> 必ず、申告に依存しない第二の帳簿を突き合わせる。**

これはエージェントに限らない。CI の実行記録も、デプロイのログも、監査証跡も同じである。

### 正直に書いておく限界

**この第二の帳簿が拾った回は、いまなお停止条件の連続数には入っていない。**
台帳に行が無いので、連続を数える対象そのものが存在しないからである。

**「見えるようになった」と「数えられるようになった」は別である。**
第 5.2 節で「量が無かった」と突かれ、量を作った翌日に
「読む側が末尾で躓いていた」と分かったのと、同じ距離がここにも残っている。

本書は、これを解決済みとして書かない。
**気づいていない穴と、気づいて残している穴は、別のものである。**
後者は記録できる。記録された穴は、次の回の誰かが塞げる。

## 5.5 未知を既定値に潰さない

もう 1 つ、計器の設計で繰り返し出てくる型がある。

上の連続数を数える処理には `?`（未クローズ）という印が出てくる。
当初、この 1 文字は **3 つの別の状態を潰していた。**

| 実際の状態 | 意味 | 連続に数えるべきか |
|---|---|---|
| (a) 締めの機構ができる前の回 | **原理的にもう閉じられない** | 数えない |
| (b) 締めを飛ばした・途中で死んだ回 | **本物の信号** | **数える** |
| (c) いま走っている回 | 正常。まだ閉じる番が来ていない | 数えない |

3 つを同じ「未クローズ」として毎回数えると、どうなるか。

計器は毎回「未クローズ 8 件」と警告を出す。内訳は (a) が 7 件、(c) が 1 件で、
**本物の信号 (b) は 0 件だった。** つまり毎回、意味のない警告を出し続けていた。

**閉じようがない過去を毎回警告し続ける計器は、やがて読まれなくなる。**
そして読まれなくなった計器は、本物の信号が来たときも読まれない。

同じ型は、押せるかどうかを測る診断（第 4 章）でも起きた。
push 失敗の分類が 2 つしか無く、**3 つ目の理由が `unknown` に落ちて
「原因不明。今すぐ潰せ」と報告した。** 実際は良性の状態で、
規則の停止条件をそのまま適用すれば、**1 回分の稼働を丸ごと潰すところだった。**

> **分類の穴は、「知らない入力が来たとき、最悪側に倒れる」形で必ず出る。
> 既定値が「緊急事態」になっている分類器は、未知に出会うたびに誤警報を出す。**

だから、未知には「緊急事態」ではなく「**まだ分類できていない**」と言わせる。
そのうえで、良性側の分類を広げすぎないこと。
「これは良性だ」と広く取ると、本物の異常がそこに紛れて素通りする。
**両方向をテストで固定する。**

## 5.6 計器を、変異テストで固定する

ここまでの欠陥は、すべて**計器そのものの欠陥**である。
計器が壊れていることは、計器では検出できない。だからテストで固定する。

ただし、計器のテストには特有の落とし穴がある。
**「常に警告を出す」実装でも、警告を期待するテストは通ってしまう。**

だから、テストは必ず対で書く。

```bash
# 検出器: 薄い回が3回続いたら停止条件を出す
ledger; row 1 -; row 2 -; row 3 -; row 4 open
grep -q '薄い回が 3 回連続' <<<"$(round gaps 12)"

# 煙感知器: 濃い回が続いている間は出さない（「常に出す」実装をここで落とす）
ledger; row 1 +; row 2 +; row 3 +; row 4 open
grep -q '薄い回が' <<<"$(round gaps 12)" ; [ $? -ne 0 ]

# 偽陽性の固定: いま走っている回を薄い回に数えて「1回早く」出さない
ledger; row 1 +; row 2 -; row 3 -; row 4 open
grep -q '薄い回が' <<<"$(round gaps 12)" ; [ $? -ne 0 ]
```

**3 本目が要る理由が、この節の要点である。**

上の 1 本目と 2 本目は、5.3 節の欠陥（末尾で遡りが切れる）を**元に戻す変異では落ちない。**
`?` を薄い回と数える規則が後から入ったため、末尾を数に入れても連続が 3 に届いてしまうからだ。
つまり 1・2 本目は「元の欠陥の再発」は捕まえるが、**末尾の扱いそのものは固定していない。**
末尾を数に入れた実装は、こんどは 1 回早く警告を出す。**そちらの向きで固定する。**

そして、テストが本当に何かを守っているかは、**わざと壊して確かめる。**
変異テストである。実装を壊し、テストを走らせ、
**落ちるべきテストが落ちるべき数だけ落ちるかを見る。**

題材のリポジトリでは、4 種類の変異でこれを確認している。
古い台帳実装に戻すと 2 件、診断を古い形に戻すと 1 件、
push を強制する形にすると 3 件、締めの処理を古い形にすると 1 件が落ちた。

**「テストが通った」は、テストが何かを守っている証拠にならない。**
落ちるべきときに落ちることを、一度は目で見る。

執筆時点で、このリポジトリの検査は 111 件ある。
そのうち停止条件が実際に発動できるかを見る節が 9 件、
台帳を書かずに走った回を拾えるかを見る節が 8 件である。
**計器の検査が全体の 15% を占めている。** 計器が嘘をつけば、その上に立つ判断が全部ずれる。

## 5.7 計器の設計原則

本章で得られたものを、実装に落とせる形で並べる。

**1. 条文より先に、参照する量を作る。**
「薄い回が 3 回続いたら止まる」は、薄さを判定する量が無ければ文字列にすぎない。
**条文を書いたら、その条文が読む変数はどこにあるかを、その場で答える。**

**2. 計器を足したら、実際に読まれる経路で両方向を試す。**
関数が正しくても、呼ばれる文脈で必ず躓くなら、その計器は存在しないのと同じである。
**発動する側と、発動しない側を、実際の呼ばれ方で。**

**3. 自己申告の帳簿には、申告に依存しない第二の帳簿を当てる。**
台帳に対するコミット履歴のように、**本人が書かなくても残る痕跡**を突き合わせる。

**4. 未知を既定値に潰さない。**
分類できない入力は「緊急事態」ではなく「まだ分類できていない」と言わせる。
**既定値が最悪側に倒れる分類器は、未知に出会うたびに誤警報を出し、やがて読まれなくなる。**

**5. 意味の無い警告を出し続けない。**
閉じようがない過去を毎回警告する計器は、本物の信号が来たときも読まれない。

**6. 計器そのものをテストで固定し、変異させて検出力を確かめる。**
「常に警告を出す」実装で通るテストは、何も守っていない。**必ず対で書く。**

**7. 塞げていない穴は、塞げていないと書く。**
第二の帳簿が拾った回は、まだ連続数に入っていない。
**「見えるようになった」と「数えられるようになった」は別である。**
記録された穴は、次の回が塞げる。記録されない穴は、次の回が同じ場所で転ぶ。

## 5.8 この章のまとめ

自己改変できるエージェントには、外側に壁が無い。だから制約より計器が先に来る。

そして本章の 3 段階は、すべて**同じ 1 つの型の再演**だった。

| 段階 | 何が無かったか |
|---|---|
| 5.2 | 条文はあった。**参照する量が無かった** |
| 5.3 | 量はできた。**読む経路が末尾で必ず躓いた** |
| 5.4 | 経路は通った。**帳簿が 1 冊しか無く、申告しない回が見えなかった** |

3 回とも、**前の段階を直した当人が、次の段階に気づいていなかった。**
これは能力の問題ではなく、**計器を作る作業に内在する構造**だと考えている。

計器を作るとき、人は「測る対象」に注意を集中する。
**計器が置かれる場所、読まれる時刻、書き手が誰かは、注意の外に落ちる。**
だから欠陥は毎回、測る対象そのものではなく、**その 1 つ外側**に出る。

> **計器を作ったら、次に問うのは「それは正しく測るか」ではなく、
> 「それは、実際に読まれる形をしているか」である。**

次章では、この計器の上に立つ規則そのものを扱う。
**自分で自分を縛る条文を書いたエージェントが、その条文を書いた当日に、
自分で書いた条文の隙間を使った記録**から始める。
