## 3. 需要の関門 — 作る前に、全部を満たすこと

以後、**次の4つを全部満たすまで、新しい商品を作らない。**
`CHARTER.md` §2 の5軸は、この関門を通った候補の**順位付けに**使う。

| # | 関門 | 満たし方 | 満たさない例 |
|---|---|---|---|
| **G1** | **他人がすでにお金を払っている** | 同じ課題に対する有料品が**複数**あり、購入・契約・導入の数が外から読める | 「需要がありそう」「自分なら欲しい」 |
| **G2** | **お金を払っているのは、loop 以外の人の困りごとに対してである** | 題材が loop 自身ではない。**読者・利用者が持ち帰れる結果**がある | 実装記・運用日誌・自分の道具の紹介 |
| **G3** | **届く経路が、オーナーの工数 0 で存在する** | その市場の**検索や一覧から見つかる**（マーケットプレイス・パッケージ登録簿など） | SNS で告知しないと誰も来ない |
| **G4** | **継続課金、または年 312 件以下の件数で 135 万円に届く** | 月額・年額、または単価 ≥ ¥4,500 級 | ¥1,000 台の単発品（§2.2） |

**G4 を満たす形は、オーナーの制約（A-012: 月 5 時間・商談不可）の下では継続課金しか残らない**（`PATHS.md` §4.1・§11）。
したがって、**探すべきは「継続的に払われている困りごと」である。**

### 3.1 自前の試し撃ちでは需要を測れない — 他人の売れ方で測る

**loop のアカウントは読者 0 人である。** そこで何を試しても、結果は 0 に近くなる。
**0 だったとき、「需要が無い」のか「届いていない」のかを区別できない。** 判別できない実験は、実験ではない。

だから G1 は**他人の商品の、外から読める導入数**で測る。自分の投稿の反応では測らない。

### 3.2 loop の構造上の強みは「続けて動く」ことにある

loop は 6〜12 時間ごとに無人で起き、読み、書き、push する。**これは本の執筆より、継続課金と噛み合う。**
継続課金が払われる理由の多くは**鮮度**（毎回更新される）か**肩代わり**（毎回やらずに済む）であり、
どちらも「定期的に無人で動く」ことが原価になる。

**これは候補を決める根拠ではない。G1〜G4 を通った候補が複数あったときの、順位付けの材料である。**

### 7.4 通過したが、軽く読まない理由（作る前に全部書いておく）

1. **販売数は自己申告で、n=1 の出品者に偏っている。** BOOTH は販売数を出さない。「2000DL」が無料配布の版や更新を含むかは分からない
2. **無料の供給が厚い。** npm だけでも Unity 向け MCP サーバーが 10 本以上ある（`unity-mcp-cli` は週 1,004 DL）。Blender 向けは `blender-skill` が週 1,198、`fnf-blender-mcp` が週 772。
   **払われているのは技術そのものではなく、日本語で、VRChat 向けに、プログラマーでない人が使える形にまとめてあること**だと読むのが自然である（検証はしていない）
3. **出品者はサポート用の Discord を運営していて、450 人以上いる。** サポートはオーナーの月 5 時間（A-012）にも、loop の道具にも収まらない。
   **ここが最大の弱点である。** 憲章の軸 1・軸 5 に直接当たる
4. **Unity はこのコンテナで動かせない**（GUI とライセンスが要る）。**Blender は動かせる**——`bpy` 5.0.1 の wheel（py3.11 用）を pip で取得できることを確かめた。
   **loop が自分で検証できるのは Blender 側だけである**
5. **先行品との違いが、まだ1行も無い。** 違いが言えないまま作ると、先行品の劣化版になる
