## 1. 終わったの定義

**年間の売上が 135 万円に到達した時点で、このプロジェクトは終わりである。**

ここまでは指示のとおり。以下は自分が置いた作業定義であり、**オーナーが上書きできる。**

| 項目 | 作業定義 | なぜそう置いたか |
|---|---|---|
| 「収益」 | **年間の入金額（売上）** | 「収益」は会計では売上を指す。所得の意味なら目標はさらに遠くなるので、**甘い側ではなく厳しい側の解釈を採らない**代わりに、台帳で売上と経費の両方を追い、どちらの定義でも測れる形にする |
| 「年」 | **初回入金から12か月の移動合計** | 暦年で切ると、12月に立ち上げた年が構造的に失敗になる |
| 到達の判定 | **オーナーが実際の入金額を出し、loop が台帳に書く** | 数字の出所は外部にある。自己申告で達成を宣言しない |

### 扶養範囲内について — ここは確認が要る（保留ではなく、依頼として立てる）

**135 万円という数字は、社会保険の扶養判定でよく使われる 130 万円の目安を上回る。**
放置すると「達成した瞬間に条件違反」になりうるので、事実として先に置く。

- **税の扶養と社会保険の扶養は、別の制度で、別の基準である。** 片方だけ見て安全とは言えない
- 社会保険の被扶養者認定は年収 130 万円未満が一般的な目安とされる。ただし**事業所得の場合に
  売上からどこまで経費を引けるかは、加入している健保組合によって扱いが違う**
- 税のほうは合計所得金額（売上 − 経費 −（青色申告なら特別控除））で判定される。
  売上 135 万円でも、経費と控除次第で所得は大きく下がりうる

**自分は税や社会保険の専門家ではない。上は一般論であって、この件の答えではない。**
`ASKS.md` に「135 万円は売上か所得か」「加入している健保組合の判定基準」を依頼として立てた。
**回答が来るまで作業は止めない。** 商品を作る工程は、この答えに依存しないからである。
依存するのは**目標額そのもの**なので、回答が来たら数字を書き換える。

## 2. 何を作るか — まだ決めていない。決め方と期限を先に置く

「売れるもの」は委任である。**委任は「決めてよい」であって「決めなくてよい」ではない。**

### 決定期限

**次の定期発火から数えて2回以内（＝ 2026-09-04 中）に、作るものを1つに決める。**
期限を切る理由は、調査が無限に続けられるからである。
**調べ続けている状態は、決めていない状態と区別がつかない。**

### 評価軸（この5つで候補を採点する）

| 軸 | なぜこの軸か |
|---|---|
| **1. オーナーの継続工数がゼロに近いか** | 制約ファイルが「オーナーの注意」を金より希少な通貨として名指ししている。毎日手が要る商品は、達成前に破綻する |
| **2. 集客がプラットフォーム内で完結するか** | 自分は外部サービスに書き込めない（禁止事項5）。SNS 運用も広告出稿も出来ない。**検索で見つかる場所に置く以外の集客手段が無い** |
| **3. 自分の出力（コードと文章）が品質を決めるか** | 12時間ごとに走る自分の唯一の強みがここにある。写真・動画・対人交渉が支配的な商品は、自分の強みが効かない |
| **4. 単価 × 必要販売数が現実的か** | 135 万円 ÷ 単価 = 必要販売数。これが桁で無理なら、その候補は最初から落ちている |
| **5. 在庫・原価・サポートの継続負担がゼロか** | 物理在庫と有人サポートは、1と5の両方を壊す |

### 候補（暫定。調査で入れ替わる）

1. デジタル商品（テンプレート・素材・データセット）をプラットフォームに置く
2. 有料記事・技術同人誌
3. ブラウザ拡張／エディタ拡張の有料版
4. ニッチな月額 Web サービス
5. 開発者向け API / データ提供

**現時点の傾き（仮説として登録済み）:** 軸2（集客がプラットフォーム内で完結する）が、
**5つの中で唯一、自分の努力では動かせない軸**である。したがって候補の順位は、
品質や単価ではなく**軸2で先に絞られる。** 調査はここから始める。

線を動かせるのはオーナーだけである。動かされるまで、こちらからは越えない。

## 4. 報告の出口 — 指示どおりにいかない部分がある

指示は「PR コメントでよい」だった。**そのままでは半分しか実行できない。**

定期発火セッションの `allowed_tools` を実測した（2026-09-03）。

```
["Bash","Read","Write","Edit","Glob","Grep","WebFetch","WebSearch"]
```

**`mcp__github__*` が無い。つまり定期発火の回は、PR の作成もマージもコメントも出来ない。**
`git push` は素の HTTPS なので通る。記録は残せるが、GitHub 上では喋れない。

だから二段構えにする。

1. **一次の出口はリポジトリ内の `venture/REPORT.md`。** 発火ごとにここへ追記して push する。
   これは MCP を持たない回でも必ず動く
2. **PR コメントは、道具を持つ回が `REPORT.md` の未報告分をまとめて出す。**
   対話セッション、または `allowed_tools` に `mcp__github__*` が足された後の定期発火

**この構成は次善である。最善は 1 を経由せず直接コメントすることなので、
`ASKS.md` に「`allowed_tools` に `mcp__github__*` を足す」を依頼として立てた。**
（`allowed_tools` は `update_trigger` では変更できない。Routines UI からのオーナー操作が要る。）

## 5. 進捗をどう測るか

**売上はゼロが長く続く。ゼロを見続けても何も分からないので、手前の量を測る。**

| 段階 | 測る量 | いまの値 |
|---|---|---|
| 0. 決定 | 作るものが1つに決まったか | **未決定**（期限 2026-09-04） |
| 1. 制作 | 出品できる状態の完成品の数 | 0 |
| 2. 出品 | オーナーが実際に出品した数 | 0 |
| 3. 初回入金 | 1円でも入ったか | **未達** |
| 4. 到達 | 12か月移動合計が 135 万円 | **未達** |

**段階3が、この設計で最も重要な関門である。**
1円入るまでは、市場が存在するかどうかについて何の証拠も無い。
**作った量は証拠ではない。** 段階1をいくら積んでも、段階3に届いていなければ仮説は未検証のままである。
